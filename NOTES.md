## Git, Linux и рабочее окружение

### Место темы в `lab-storage`

Git хранит воспроизводимую историю изменений проекта. Linux — среда разработки и будущая
основа production-сервера. Поэтому это не вспомогательная настройка, а часть архитектуры и
эксплуатации.

#### Три состояния Git

Git в базовом цикле связывает три области:

1. **Working tree** — файлы на диске, с которыми я работаю.
2. **Index**, или staging area, — подготовленный снимок будущего коммита.
3. **Repository** — граф уже созданных коммитов в `.git`.

`git add` обновляет index содержимым из working tree. `git commit` создаёт новый снимок из index и
передвигает текущую ссылку ветки. `git push` передаёт локальные объекты и обновляет ссылку в удалённом
репозитории.

Удобная модель: working tree — текущее содержимое рабочего стола, index — отобранный набор для
следующего снимка, а commit — уже сохранённый снимок со ссылкой на предыдущий. Коммит хранит состояние,
а `git diff` вычисляет различие между двумя состояниями.

#### Локальная и удалённая история

Git — распределённая система: локальный репозиторий сам хранит историю. GitHub — один из удалённых
сервисов для хранения и совместной работы, а не сам Git. `ahead` означает, что в локальной ветке есть ещё
не отправленные коммиты; `behind` — что в отслеживаемой удалённой ветке есть коммиты, которых нет локально.

Для GitHub пароль учётной записи не используется как Git-пароль. Документированные варианты включают
HTTPS с токеном и SSH. Секрет нельзя класть в коммит: удаление из следующей версии не удаляет его из старой истории.

#### Linux, shell и `PATH`

Shell — командный интерпретатор. Он читает команду, выполняет подстановки и запускает встроенную команду
или отдельный процесс. `PATH` — список каталогов, в которых shell ищет исполняемый файл, если в команде не указан полный
путь.

Обычный запус скрипта создаёт дочерний процесс. Его изменения переменных не меняют родительский shell. `source`
выполняет команды в текущем shell, поэтому изменение `PATH` из `.bashrc` может сразу повлиять на текущую сессию.

Виртуальное окружение Python активируется по той же идее: скрипт добавляет `.venv/bin` в начало `PATH`. Активация
удобна, но не обязательна: можно явно вызывать `.venv/bin/python`.

#### Что хранится в Git

В историю проекта идут исходный код, SQL, тесты и файлы-рецепты окружения. Генерируемые кэши, `.venv`, секреты и
локальные служебные записи не коммитятся. `.gitignore` не удаляет уже отслеживаемый файл: он влияет на неотслеживаемые файлы.

#### Формулировки для собеседования

- Git хранит снимки состояния, а commit ссылается на родителя, формируя граф истории.
- Index позволяет явно собрать следующий коммит независимо от всех изменений working tree.
- GitHub не заменяет Git: Git работает локально, GitHub хранит удалённую копию и даёт инструменты совместной работы.
- `source` меняет текущий shell, а обычный запуск скрипта выполняется в отдельном процессе.

#### Вопросы для самопроверки

1. Чем working tree, index и commit отличаются друг от друга?
2. Почему `git diff` и `git diff --staged` могут показывать разные изменения?
3. Почему добавление файла в `.gitignore` не прекращает отслеживание, если файл уже был добавлен в Git?
4. Почему `source ~/.bashrc` может изменить `PATH` текущего shell?

### 2026-09-17 — Жизненный цикл процесса

#### Место темы в проекте

Сценарий Python, сервер приложения, PostgreSQL и контейнерные компоненты
выполняются как процессы. Умение найти нужный процесс и проверить его завершение —
основа дальнейшей работы с systemd, Docker и диагностикой сервиса.
Первую практику я выполнил на `sleep`, не затрагивая БД, файлы и сеть проекта.

#### Термины и принцип работы

Программа — код, который можно запустить; процесс — конкретный запущенный
экземпляр. PID обозначает процесс, PPID — его родителя. Номер PID не является
постоянным идентификатором программы и после завершения может использоваться повторно.

При обычном запуске `sleep 5` Bash ждёт завершения команды. Суффикс `&` запускает
команду в фоне: Bash возвращает приглашение, пока дочерний процесс продолжает работу.
Это ещё не служба с автоматическим запуском и восстановлением после отказа.

- `$!` — PID последнего фонового запуска; `lab_pid=$!` сохраняет его в переменную.
  В присваивании Bash не ставятся пробелы вокруг `=`.
- `$$` — PID Bash в нашем опыте; `$lab_pid` — значение нашей переменной.
- `ps -p "$lab_pid" -o pid,ppid,stat,etime,args` выбирает процесс и поля вывода:
  его PID, родителя, состояние, время с запуска и команду с аргументами.
- `S` обозначает прерываемое ожидание события. Для `sleep` ожидание таймера
  нормально: существование процесса не означает постоянную загрузку CPU.

Сигнал — уведомление процессу. `kill -TERM "$lab_pid"` отправляет SIGTERM, а не
доказывает завершение прикладной работы. Программа может обрабатывать сигнал;
корректное освобождение ресурсов и сохранение данных не обеспечиваются одним
названием SIGTERM. Успех команды отправки и результат работы адресата различаются.

`wait "$lab_pid"` ожидает завершения своего дочернего процесса и возвращает его
статус. `$?` содержит статус последней команды, поэтому его проверяют сразу после
`wait`. В Bash завершение от сигнала N представляется статусом `128 + N`.
Для SIGTERM с номером 15 в этом опыте получен код 143.

#### Что я выполнил и подтвердил

Я прислал вывод своего терминала после следующего опыта:

| Наблюдение | Результат |
| --- | --- |
| Запуск на переднем плане | `sleep 5` завершился, приглашение вернулось |
| Фоновый запуск | `sleep 600 &`, PID `215314` |
| PID Bash | `215225` |
| Родитель sleep по ps | PPID `215225`, совпал с PID Bash |
| Состояние и время наблюдения | `S`, `04:40`, команда `sleep 600` |
| После SIGTERM | Bash сообщил `Terminated` |
| После wait и немедленного echo $? | `143` |

Это исторические PID конкретного опыта, не номера для повторной отправки сигналов.
Финальную строку `ps` после остановки я в чат не присылал; завершение дочернего
процесса подтверждено результатом `wait`. Статус самой команды `kill` отдельно
в присланном выводе не измерялся.

#### Разбор результата и понимание

Ошибок команд в присланном выводе не обнаружено. Я объяснил, что успешная отправка
сигнала сама по себе не гарантирует завершения программы, поэтому требуется
проверка результата адресата. Полученные `143` здесь ожидаемы: это следствие
намеренно отправленного SIGTERM, а не самостоятельный сбой приложения.

Общая ловушка: `echo $?` после `kill` относится к отправке сигнала, после `wait` —
к полученному статусу дочернего процесса, а после `ps` — уже к проверке процессов.
Вставленная между ними команда меняет смысл наблюдения.

### 2026-09-18 — Стандартные потоки и логи

#### Место темы и теория

Чтобы сопровождать lab-storage, нужно сохранять результаты и диагностические
сообщения независимо от открытого терминала. Для первой практики достаточно
перенаправить существующий вывод [`main.py`](main.py), не изменяя Python-код.

Стандартные потоки процесса: stdin (дескриптор 0), stdout (1), stderr (2).
Дескриптор — числовое обозначение открытого канала ввода-вывода в процессе.
Обычно stdout и stderr при интерактивном запуске направлены в один терминал,
поэтому визуально сообщения выглядят одним потоком. Однако программа выбирает
канал сама: Linux не определяет его по словам в сообщении.

В Python `print()` по умолчанию использует stdout; сообщения об ошибках самого
интерпретатора идут в stderr. Содержимое stderr и код завершения — разные
источники информации: диагностический текст сам по себе не доказывает неуспех,
а отсутствие текста не доказывает успех.

| Окончание команды | Поток | Что происходит с файлом |
| --- | --- | --- |
| `> output.log` | stdout | Создание или очистка существующего содержимого |
| `>> output.log` | stdout | Добавление в конец без удаления прежнего содержимого |
| `2> error.log` | stderr | Создание или очистка существующего содержимого |
| `2>> error.log` | stderr | Добавление в конец без удаления прежнего содержимого |

Без номера у выходного перенаправления подразумевается дескриптор 1.
Номер пишется вплотную к оператору: `2>` и `2 >` не равнозначны.
Как аналогия с Python, `>` похож на режим `"w"`, а `>>` — на `"a"`, но файл
открывает Bash ещё до выполнения команды. Ошибка последующего запуска не
восстанавливает содержимое, которое уже было очищено перенаправлением.

#### Что я выполнил

- Запустил `python main.py`, направив stdout и stderr в отдельные файлы
  `uploads/streams-demo/output.log` и `uploads/streams-demo/error.log`.
- Повторил успешный запуск с `>>`, сохранив первый вывод.
- Попросил Python запустить несуществующий `uploads/streams-demo/absent.py`,
  направив диагностику через `2>>` в error.log.
- После каждого запуска сразу проверил `echo $?`; прислал статусы `0`, `0`, `2`.

Использовал активное окружение venv и команду `python`, что в этом опыте допустимо.
Во втором запуске перенаправлял только stdout: возможная диагностика этого
конкретного запуска осталась бы в терминале, а не в error.log.

#### Проверка результата

Codex прочитал файлы 2026-09-18, не перезапуская команды поверх моих логов:

- В output.log — 16 строк: два полных вывода main.py по 8 строк.
  Начала выводов находятся на строках 1 и 9, завершающий `None` — на 8 и 16.
- В error.log — одна строка: Python сообщает, что не может открыть отсутствующий
  файл сценария. Ошибка не смешалась с накопленным результатом программы.
- Статусы `0`, `0`, `2` подтверждены присланным выводом терминала, а не
  восстановлены из файлов: текст лога не хранит код завершения автоматически.
- Проверка `git check-ignore` подтвердила, что оба учебных лога исключены из Git
  правилом `uploads/`. Python-код для этой практики не изменялся.

#### Наблюдения и самопроверка

`2>>` вместо предложенного `2>` — допустимый вариант: я выбрал добавление
диагностики, а не очистку предыдущих сообщений. Отсутствие пробела между `2>>`
и путём файла также допустимо. При повторных ошибочных запусках сообщения будут
накапливаться, что нужно учитывать при чтении лога.

Код `2` в последнем запуске ожидаем для наблюдаемой ошибки открытия сценария;
перенаправление сообщения не превращает неуспех в успех. Команды и файлы
практически проверены. Для проверки понимания разобран прогноз:

Если при запуске отсутствующего сценария заменить `2>> error.log` на
`> output.log`, что произойдёт с ранее накопленным output.log и где появится
сообщение об ошибке? Это мысленная проверка, не команда для очистки учебного лога.

В первом ответе я верно предсказал потерю прежнего содержимого output.log, но
ошибочно предположил, что сообщение об ошибке запишется в этот же файл,
поскольку stderr отдельно не перенаправлен.

Разбор ошибки прогноза: `>` меняет только назначение stdout (дескриптор 1).
Stderr (дескриптор 2) не переключается на stdout при неуспешном запуске и в нашем
терминале остаётся направленным на экран. Bash сначала очищает output.log,
затем Python сообщает о несуществующем сценарии через stderr. Ожидаемый итог:
output.log пуст, сообщение видно в терминале. Ошибка программы не меняет
маршрут потоков автоматически. Существующие логи при разборе не перезаписывались.

В следующем прогнозе про `>>` я уже верно указал, что ошибка будет видна в
терминале, но назвал output.log пустым. Здесь отдельно уточняется исходное
состояние: в настоящем файле по повторной проверке всё ещё 16 строк; предыдущий
вариант с очисткой через `>` обсуждался только мысленно. Для отдельного запуска
с `>>` старые 16 строк сохранятся, новых строк из stdout не добавится. Если же
изначально файл уже пуст, то без нового вывода он действительно останется пустым.
Общее правило: отсутствие новых данных не удаляет старые; очистку вызывает `>`,
а не сам факт ошибки программы. В следующем ответе я уточнил прогноз: при `>>`
прежние 16 строк останутся, а из ошибочного запуска в stdout ничего не добавится.
Различие очистки через `>` и сохранения содержимого через `>>` подтверждено
моим объяснением.

#### Stdin и конвейер: проверенная практика

Я сравнил три способа передать данные `wc -l` и заранее предсказал, что команда
в конвейере покажет количество строк:

```text
wc -l uploads/streams-demo/output.log  -> 16 uploads/streams-demo/output.log
wc -l < uploads/streams-demo/output.log -> 16
python main.py | wc -l                  -> 8
```

В первом случае `wc` сам получил путь как аргумент командной строки, открыл файл
и поэтому включил его имя в результат. Во втором случае файл открыл Bash и
подключил его к stdin команды `wc`: самой программе имя файла не передавалось.
В третьем случае Bash соединил stdout `python main.py` со stdin `wc -l`, поэтому
`wc` получил восемь строк как поток данных без имени файла.

Я верно объяснил различие между аргументом-путём и входным потоком. Этот опыт
подтвердил направление данных в конвейере слева направо. В обычном `|` передаётся
stdout левой команды; stderr не входит в этот канал автоматически.

### 2026-09-18 — Переменные окружения процессов

#### Место темы и теория

Lab-storage должен получать настройки без зашитых в код значений. Окружение
процесса представляет собой набор строковых пар `имя=значение`, который процесс
получает при запуске. Обычная переменная Bash остаётся внутри текущего shell;
`export` добавляет её в окружение последующих дочерних процессов.

Наследование направлено от родителя к создаваемому ребёнку. Запись вида
`ИМЯ=значение команда` изменяет окружение только на время этой команды. В Python
`os.getenv("ИМЯ")` возвращает строковое значение или `None`, если имени нет.
Окружение процесса и Python `venv` — разные механизмы: `venv` выбирает интерпретатор
и набор пакетов, но не является отдельным каналом конфигурации приложения.

#### Что я выполнил и подтвердил

Я последовательно проверил локальную переменную Bash, `export`, временное
присваивание перед командой и `unset`. Получен ожидаемый вывод:

```text

None
development
testing
development
None
```

До `export` текущий Bash видел своё значение, а новый процесс Python не получил
его. После `export` следующий Python увидел `development`. Временное значение
`testing` было доступно только одному запуску; родительский Bash сохранил
`development`. После `unset` новый Python снова получил `None`.

Я правильно объяснил область видимости и передачу значения дочернему процессу.
Точность терминологии: значение увидел процесс Python, а не «Python-окружение»;
активированный `.venv` к самому механизму наследования переменных не относится.

### 2026-09-18 — UID, GID, права и umask

#### Место темы и теория

Доступ процесса к файлам определяется его числовыми UID/GID, владельцем и
группой объекта, а также битами прав для владельца, группы и остальных.
Для обычного файла `r`, `w`, `x` означают чтение, запись и выполнение. Для
каталога эти биты управляют перечислением имён, изменением записей и проходом
к объектам внутри каталога.

При создании `touch` обычно запрашивает для файла режим `0666`, а `mkdir` для
каталога — `0777`. `umask` очищает запрещённые биты; это не арифметическое
вычитание. Формально итоговый режим можно представить как
`requested_mode & ~umask`. Маска не может добавить право, которого не было в
запрошенном режиме.

#### Что я выполнил и подтвердил

- `id` показал UID `1000`, основной GID `1000` и дополнительные группы текущего
  пользователя, включая `sudo` и `lxd`.
- Исходный и финальный `umask` равны `0002`.
- При исходной маске файл получил `0664`, каталог — `0775`.
- В subshell с `umask 027` файл получил `0640`, каталог — `0750`.
- После завершения subshell маска родительского Bash осталась `0002`.

Codex повторно проверил режимы через `stat`; владелец и группа всех учебных
объектов — `sergey:sergey`. Каталог находится под `uploads/` и исключён из Git.
Дополнительные вызовы `ll -d`, `ls -ld` и `ls -l` без нужных путей только вывели
данные рабочего каталога и не повредили результат опыта.

#### Ошибка в объяснении

Симптом: я описал результат как обычное вычитание `666 - 027 = 640` и назвал
`666` полным доступом. Режимы совпали с ожидаемыми, но правило сформулировано
неверно.

Причина: восьмеричные цифры здесь кодируют независимые биты `r=4`, `w=2`,
`x=1`; маска очищает выбранные биты. `0666` означает `rw-rw-rw-` и не содержит
битов выполнения, поэтому полным доступом не является.

В контрольном вопросе для запрошенного режима `0600` и маски `0022` я сначала
ответил `0644`, снова подставив привычный исходный режим `0666`. После указания
на то, что маска не добавляет отсутствующие биты, я сам исправил ответ: итоговый
режим остаётся `0600`. Это подтвердило различие между очисткой битов и числовым
вычитанием или назначением стандартного режима.

### 2026-09-18 — Системная учётная запись сервиса

#### Место темы и решение

Lab-storage не должен работать с правами обычного пользователя или root.

В Ubuntu выбран высокоуровневый `adduser`, который применяет правила
дистрибутива. Каталог создаётся через `install -d`, чтобы назначить владельца,

#### Что я выполнил и подтвердил

- Создал системного пользователя `lab-storage` с UID `113` и одноимённую
  основную группу с GID `116`.
- У записи нет человеческого домашнего каталога: поле home равно `/nonexistent`.
- Login shell установлен в `/usr/sbin/nologin`.
- Каталог `/var/lib/lab-storage` имеет режим `0750` и владельца
  `lab-storage:lab-storage` по выводу моего терминала.
- Команда `sudo -u lab-storage touch` завершилась со статусом `0`.
- Обычный `touch` от `sergey` завершился `Permission denied` и статусом `1`.
- Обычный `stat` вложенного файла также получил `Permission denied`: у категории
  others нет бита `x` на каталоге, необходимого для прохода к объекту.

#### Ошибка в объяснении

Я сначала назвал `sudo -u lab-storage` запуском с повышенными правами и предложил
добавить сервисную учётную запись в группу `sudo`. Это смешивает право человека
просить `sudo` о смене пользователя с правами целевого процесса.

Фактически `sudo -u lab-storage` запускает команду с UID `lab-storage`, а не
root. Именно этот UID совпадает с владельцем каталога и выбирает биты `7` из
режима `0750`. Членство `sergey` в группе `sudo` само по себе не отключает
обычные проверки доступа. Добавление демона в `sudo` нарушило бы принцип
наименьших привилегий и не является исправлением.

После разбора я правильно переформулировал результат: первый `touch` выполнялся
с UID `lab-storage`; `sergey` не смог пройти к файлу из-за отсутствия прав;

проверка положительного и отрицательного сценариев завершены.

### 2026-09-18 — Inode и жёсткие ссылки

#### Место темы и теория

Имя файла хранится в записи каталога и указывает на inode внутри файловой
системы. Inode содержит метаданные и связан с данными, но не хранит имя файла.
Жёсткая ссылка создаёт ещё одну пару «имя → тот же inode», а не копию данных.
Счётчик ссылок inode показывает количество таких имён.

`unlink` удаляет одно имя. Inode и данные освобождаются только после удаления
последней жёсткой ссылки и закрытия всех открытых файловых дескрипторов. Поэтому
слово «удалить файл» в эксплуатации нужно уточнять: исчезновение пути ещё не
всегда означает немедленное освобождение блоков.

#### Что я выполнил и подтвердил

- Создал `original.txt`, затем второе имя `second-name.txt` командой `ln`.
- Проверил через `stat`, что оба имени указывали на одинаковый inode, а счётчик
  ссылок стал равен двум.
- Добавил строку через второе имя и прочитал её через первое, подтвердив общие
  данные.
- Удалил `original.txt`; второе имя сохранило содержимое.

Codex повторно проверил рабочее дерево: `original.txt` отсутствует,
`second-name.txt` указывает на inode `7866304`, имеет одну жёсткую ссылку, размер
23 байта и две ожидаемые строки. Учебный каталог находится под игнорируемым
`uploads/`.

#### Что я понял

В первоначальной формулировке я сказал, что удалился inode, но сразу поправился:
удалилась запись каталога с одним именем. Оставшееся имя продолжило указывать на
тот же inode и данные. Место также может оставаться занятым из-за другой жёсткой
ссылки; следующий опыт отдельно проверяет второй случай — открытый дескриптор
процесса после удаления последнего имени.

#### Официальные источники

- [Linux man-pages: `unlink()`](https://man7.org/linux/man-pages/man2/unlink.2.html)
- [uutils Coreutils: `stat`](https://uutils.org/coreutils/docs/utils/stat.html)

### 2026-09-18 — Удалённый, но открытый файл

#### Место темы и механизм

После `open` процесс получает файловый дескриптор, связанный через открытый
объект ядра с inode. `unlink` последнего имени обнуляет счётчик жёстких ссылок,
но inode и блоки данных сохраняются, пока остаётся хотя бы одна открытая ссылка
из процесса. Поэтому удаление большого журнала не гарантирует немедленного
возврата места файловой системе.

`lsof +L1` выбирает открытые файлы со счётчиком жёстких ссылок меньше единицы.
Каталог `/proc/PID/fd` показывает дескрипторы процесса; путь удалённого объекта
помечается как `(deleted)`.

#### Что я выполнил и понял

- Запустил `tail -f` в фоне и сохранил его PID.
- Удалил последнее имя `second-name.txt`, пока `tail` держал файл открытым.
- Нашёл удалённый объект через `lsof` и список дескрипторов процесса.
- Завершил `tail` через SIGTERM, дождался его через `wait` и удалил пустой
  учебный каталог.

Я заранее верно предсказал, что имя исчезнет из каталога, но объект останется
виден через открытый дескриптор до остановки `tail`. В ответе сначала назвал

ядро закрыть все принадлежавшие ему дескрипторы. Процесс мог бы вызвать `close`
и продолжить работу с тем же результатом для файла.

`tail` не осталось, а `lsof +L1` не показывает путь учебного файла.

### 2026-09-19 — Точка монтирования и учёт места

#### Место темы и теория

Файловая система организует каталоги, inode и блоки данных. Точка монтирования
— каталог, через который дерево этой файловой системы подключено к общему
дереву путей Linux. Источник файловой системы может быть разделом диска,
логическим или сетевым томом либо другим поддерживаемым объектом.

`findmnt --target` определяет файловую систему, содержащую заданный путь. `df`
показывает учёт блоков или inode для всей файловой системы, на которой находится
путь. `du` обходит доступное по именам дерево переданного каталога и оценивает
занятое им место. Поэтому эти команды отвечают на разные вопросы и их значения
не обязаны совпадать.

#### Что я выполнил и подтвердил

- `findmnt` показал для проекта точку монтирования `/`, источник
  `/dev/nvme0n1p7` и файловую систему `ext4` с параметрами `rw,relatime`.
- `df -hT` показал для всей файловой системы 203 ГБ, из которых занято 44 ГБ,
  доступно 149 ГБ, использование — 23%.
- `df -hi` показал около 13 миллионов inode, из которых использовано 447 тысяч,
  или 4%.
- `du -shx .` оценил дерево проекта в 185 МБ. Из них `.venv` занимает 169 МБ,
  `.git` — 3,2 МБ, а `uploads` — 28 КБ.

Я заранее правильно предсказал, что `Used` из `df` будет намного больше размера
проекта из `du`: первая команда учитывает всю файловую систему, вторая — только
переданное дерево. Я также правильно связал удалённый, но открытый файл с `df`:
его блоки остаются учтёнными файловой системой, хотя `du` уже не может найти
объект обходом имён. В итоговой фразе я случайно написал `df` вместо `du`; это
опечатка, а не ошибка в понимании механизма.

#### Особенность проверки

Первая повторная проверка Codex выполнялась в изолированном mount namespace и
показала служебный bind mount проекта. Эти данные не были выданы за состояние
хостовой Ubuntu. Повторная read-only проверка вне изоляции подтвердила реальные
значения `/`, `/dev/nvme0n1p7` и `ext4`. Результаты команд всегда относятся к
пространству монтирования того процесса, который их запустил.

### 2026-09-19 — Наблюдение дискового I/O

#### Место темы и теория

Дисковый I/O — обмен данными с блочным устройством. Скорость передачи,
количество запросов, задержка, очередь и время занятости описывают разные
стороны нагрузки. Одно число не заменяет остальные и не доказывает само по себе
наличие или отсутствие насыщения.

`iostat` вычисляет показатели из счётчиков ядра. С параметром `-y` первый отчёт
со средними значениями от загрузки системы пропускается; последующие отчёты
описывают заданные интервалы. В расширенном отчёте `w/s` показывает завершённые
операции записи в секунду, `wkB/s` — пропускную способность записи, `w_await` —
среднее время запроса с очередью и обслуживанием, `aqu-sz` — среднюю очередь,
а `%util` — долю интервала с выданными устройству запросами. Для современного
параллельного SSD `%util` не является прямым пределом производительности.

#### Что я выполнил и подтвердил

- Запустил 20 секунд расширенного наблюдения `iostat` с интервалом одна секунда
  и сохранил отчёт в `uploads/iostat-write.log`.
- Создал временный файл из 2048 блоков по 1 МиБ через `dd`; источником был
  `/dev/zero`, а `conv=fdatasync` потребовал записать данные до завершения.
- После опыта удалил `uploads/io-demo.bin`. Codex подтвердил отсутствие файла,
  завершение `iostat`, наличие всех 20 отчётов и корректность Git diff.

В пиковом интервале для `nvme0n1` получены следующие значения:

| Показатель | Значение |
|---|---:|
| `r/s` | 6 |
| `rkB/s` | 112 КиБ/с |
| `w/s` | 17 136 |
| `wkB/s` | 2 157 944 КиБ/с |
| `w_await` | 2,13 мс |
| `wareq-sz` | 125,93 КиБ |
| `aqu-sz` | 36,51 |
| `%util` | 37,10% |

Разница между 112 КиБ/с чтения и примерно 2,06 ГиБ/с записи подтверждает, что
наблюдалась именно нагрузка записи. После пика большинство интервалов снова
стали пустыми или малонагруженными; `-z` скрыл полностью неактивные устройства.

#### Вывод и уточнение ответа

Я правильно спрогнозировал рост показателей записи и объяснил, что синтетическая
скорость `dd` не гарантирует производительность будущего сервиса. Более точная
формулировка: наличие записи прежде всего доказывают `w/s` и `wkB/s`.
`w_await` и `aqu-sz` описывают задержку и накопление запросов, но при быстрой или
малой записи могут оставаться низкими. Поэтому не обязательно, чтобы каждый
связанный с записью показатель заметно вырос при любой записывающей нагрузке.

Одиночный последовательный поток нулевых данных не воспроизводит размеры
файлов лаборатории, конкурентные загрузки, чтение, обработку HTTP, PostgreSQL,
кэширование и соседнюю нагрузку. `fdatasync` делает завершение опыта честнее по
отношению к фактической записи, но не превращает `dd` в модель всего сервиса.

### 2026-09-19 — Один CPU и load average

#### Место темы и теория

Логический CPU — вычислительный исполнитель, доступный планировщику ядра.
Значение `%CPU` процесса в `ps` около 100% обычно означает использование одного
логического CPU, тогда как CPU-проценты `vmstat` усреднены по всей системе.

Load average — не процент загрузки CPU. Это сглаженное за 1, 5 и 15 минут число
задач в состояниях runnable (`R`) и непрерываемого ожидания (`D`). Значение не
нормализовано по количеству CPU и не обнуляется сразу после исчезновения
нагрузки. В `vmstat` столбец `r` показывает текущие runnable-задачи, `b` —
задачи, заблокированные в ожидании I/O, а `us`, `sy`, `id` и `wa` делят
общесистемное процессорное время.

#### Что я выполнил и подтвердил

- `nproc` показал 12 логических CPU, доступных процессу.
- Я запустил бесконечный вычислительный цикл Python и сохранил его PID.
- `ps` показал состояние `R`, выполнение на логическом CPU 4 и `%CPU = 100`.
- В десяти односекундных выборках `vmstat` значение `r` было в основном равно
  1 и один раз 2; `us` держалось около 9%, `sy` — 0–1%, `id` — 90–91%.
- `b` и `wa` оставались нулевыми: опыт создавал вычислительную, а не I/O-нагрузку.
- Одноминутный load вырос примерно с 0,28 до 0,53. Сразу после завершения
  процесса он был около 0,54, что подтвердило инерцию сглаженного показателя.
- Процесс завершён через SIGTERM и больше не существует. Полные измерения
  сохранены в игнорируемых файлах `uploads/cpu-observation.log` и
  `uploads/vmstat-cpu.log`.

Мой прогноз подтвердился: процесс занял один CPU, а не всю машину. Я правильно
объяснил одновременные `100%` у процесса и примерно `90% id` системы отношением
одного занятого CPU к двенадцати доступным. Я также правильно связал медленное
снижение load average со сглаживанием по времени.

#### Ошибка проверки и общее правило

При первой попытке `vmstat-cpu.log` отсутствовал, а `cpu-observation.log`
содержал только последнюю строку. По одному правильному объяснению нельзя было
считать опыт выполненным. Я повторил команды в одном терминале; после этого в
логах появились снимок процесса и все десять выборок `vmstat`.

Общее правило эксплуатации: уверенное объяснение гипотезы не заменяет
наблюдаемые артефакты. Перед закрытием диагностики нужно проверить, что нужные
логи действительно созданы, относятся к требуемому интервалу и содержат
ожидаемые показатели.

### 2026-09-19 — RAM, RSS и swap

#### Место темы и теория

Процесс работает с виртуальным адресным пространством. `VmSize`/`VSZ`
показывает его виртуальный размер, а `VmRSS`/`RSS` — резидентные страницы,
которые сейчас находятся в RAM. `RssAnon` относится к анонимной памяти процесса,
например heap и выделенным буферам; `RssFile` — к резидентным страницам файлов
и библиотек; `VmSwap` — к выгруженной в swap анонимной памяти процесса.

В общесистемном отчёте `free` значение `free` означает полностью
неиспользуемую RAM. `available` оценивает, сколько памяти можно передать новым
приложениям без swap, учитывая освобождаемую часть page cache и другие
возвращаемые ресурсы. Это оценка, а не жёсткий лимит выделения памяти.

`swpd` в `vmstat` показывает уже занятое пространство swap. `si` и `so`
показывают текущую передачу страниц из swap и в swap за интервал. Поэтому
ненулевой `swpd` не означает активный обмен в данный момент.

#### Что я выполнил и подтвердил

- Создал в Python `bytearray` размером 536 870 912 байт и удерживал его живым
  для наблюдения.
- `ps` показал `VSZ = 545580 KiB`, `RSS = 533768 KiB` и 3,4% памяти системы.
- `available` уменьшился с 7,6 до 7,0 ГиБ и после SIGTERM восстановился примерно
  до 7,5 ГиБ. `used` вырос с 7,2 до 7,8 ГиБ и затем снизился до 7,3 ГиБ.
- `buff/cache` оставался около 5,4–5,5 ГиБ: нагрузка создавалась анонимным
  буфером, а не чтением обычного файла в page cache.
- Во всех десяти выборках `vmstat` `si` и `so` были равны нулю, хотя `swpd`
  оставался около 1,04 ГиБ. Во время опыта активного обмена со swap не было.
- После уточняющего измерения `/proc/PID/status` получены `VmRSS = 533740 KiB`,
  `RssAnon = 527200 KiB`, `RssFile = 6540 KiB`, `VmSwap = 0`.
- Процесс завершён через SIGTERM со статусом 143 и больше не существует.

#### Ошибки и уточнения

Я спрогнозировал, что основной частью станет `RssFile`. Это неверно: `bytearray`
создан самим процессом и не подкреплён обычным файлом, поэтому его страницы
относятся к `RssAnon`. После измерения я правильно связал анонимную память с
выделенным буфером без файлового взаимодействия.

Первоначальная команда с `rg` не выполнилась, потому что ripgrep отсутствует на
хостовой Ubuntu. Устанавливать новую зависимость ради единственной фильтрации не
потребовалось: проверка повторена штатным `grep -E` и сохранена отдельно.

В объяснении `available` я допустил условие «если `free` больше `available`».
Обычно `available` как раз больше `free`, поскольку включает оцениваемую
освобождаемую память; в опыте это были 7,6 и 4,4 ГиБ. Нулевые `si/so` доказывают
отсутствие swap I/O только в измеренных интервалах. В сочетании с 7 ГиБ
`available` это подтвердило отсутствие давления памяти именно в данном опыте,
но не является универсальной гарантией для любого момента.

### 2026-09-19 — Локальный OOM в cgroup

#### Место темы и теория

cgroup организует процессы в иерархические группы и позволяет контроллерам
ядра учитывать и ограничивать их ресурсы. Systemd помещает service units в
отдельные cgroup. Это позволяет ограничить один сервис, не создавая намеренно
дефицит памяти для всей системы.

`MemoryMax` задаёт жёсткий предел памяти unit и служит последней линией защиты;
при невозможности удержать потребление под пределом внутри unit вызывается OOM
killer. `MemorySwapMax=0` запрещает расход swap этой cgroup. `OOMPolicy=kill`
требует завершить оставшиеся процессы unit. Для штатного управления давлением
памяти systemd рекомендует использовать `MemoryHigh`, оставляя `MemoryMax`
аварийной границей.

`MemoryError` — исключение Python, которое возникает, если аллокатор не смог
получить память и интерпретатор сохранил возможность продолжить выполнение.
cgroup OOM может завершить процесс сигналом SIGKILL до возврата управления
Python; этот сигнал нельзя перехватить или обработать для очистки.

#### Что я выполнил и подтвердил

- Подтвердил единую иерархию cgroup v2 и использовал установленный systemd 259.
- Через `systemd-run --user` создал transient service с `MemoryMax=256M`,
  `MemorySwapMax=0`, `OOMPolicy=kill` и попыткой выделить 512 МиБ.
- Systemd зафиксировал `ActiveState=failed`, `SubState=failed`,
  `Result=oom-kill`, `ExecMainCode=2`, `ExecMainStatus=9`.
- `MemoryPeak=268435456` байт в точности совпал с лимитом 256 МиБ.
- Журнал сообщил: kernel OOM killer завершил Python через SIGKILL; основной
  процесс завершился с `status=9/KILL`, unit получил результат `oom-kill`.
- Опыт занял около 128 мс и не исчерпал память хоста.
- После сохранения доказательств я выполнил `reset-failed`; Codex подтвердил,
  что transient unit и его cgroup больше не существуют.

Мой прогноз полностью подтвердился: процесс не удержал 512 МиБ, был уничтожен
сигналом, а память всей Ubuntu не закончилась.

#### Уточнение ответа

Я сначала сказал, что `MemoryError` «проверяет всю системную память». Это
неточно: Python не выполняет такую отдельную проверку. Исключение появляется,
когда запрос его аллокатора завершается неудачно, но интерпретатор остаётся жив
и способен создать исключение. В опыте ядро применило SIGKILL внутри cgroup,
поэтому Python не получил возможности вернуть `MemoryError`.

Одного `Result=oom-kill` уже достаточно для сильной диагностики, но полный
набор доказательств надёжнее: `Result=oom-kill`, `ExecMainCode`/запись журнала
`code=killed`, `ExecMainStatus=9`, пик ровно на `MemoryMax` и прямое сообщение
ядра в journal.

- [systemd: `systemd-run`](https://www.freedesktop.org/software/systemd/man/latest/systemd-run.html)
- [systemd: управление ресурсами units](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html)

### 2026-09-19 — Установленная и candidate-версия пакета

#### Место темы и теория

Менеджер пакетов нужен для воспроизводимой установки и безопасного обновления
компонентов сервера. Перед обновлением production-системы важно различать уже
установленное состояние, доступные версии и предполагаемый план изменений.

`dpkg` хранит состояние установленных Debian-пакетов. `dpkg-query` читает эту
базу и показывает фактически установленную версию. APT работает поверх неё и
добавляет сведения из настроенных источников пакетов.

`apt update` загружает локальные индексы доступных пакетов из источников,
описанных в конфигурации APT. Эта команда не устанавливает новые версии.
`apt-cache policy` показывает установленную версию, candidate и таблицу версий
с источниками и приоритетами. **Candidate** — версия, которую APT предпочитает
установить с учётом текущих индексов, настроенных репозиториев, архитектуры и
политики приоритетов.

Равенство `Installed` и `Candidate` означает только отсутствие более
предпочтительной версии в текущем представлении APT. Оно не доказывает, что это
последний выпуск на сайте разработчика: upstream-релиз может ещё не попасть в
репозитории дистрибутива, а локальные индексы могут быть устаревшими.

`apt-get -s upgrade` вычисляет план обычного обновления в режиме симуляции.
Ключ `-s` запрещает выполнение изменений и отключает блокировки. Поэтому вывод
полезен для предварительного аудита, но документация предупреждает, что без
блокировок состояние системы может измениться параллельно и реальная операция
позже должна быть проверена заново.

- Через `dpkg-query` сохранил установленные версии `systemd`, `sysstat`,

  `3.14.4-1ubuntu0.2` из `resolute-updates` и `resolute-security`.
- Через `apt-get -s upgrade` безопасно получил план: 29 пакетов были бы
  обновлены, новые пакеты и удаления не планировались, 5 обновлений были
  отложены из-за phased updates.
- Разделил доказательства на локальные журналы `uploads/package-audit.log` и
  `uploads/package-upgrade-simulation.log`. Каталог `uploads/` игнорируется Git,
  поэтому проверенные числовые результаты сохранены непосредственно в этой главе.

### 2026-09-19 — Загрузочная цель и зависимости systemd

#### Место темы и теория

Systemd управляет системой через units. Суффикс имени определяет тип объекта:
`.service` описывает службу, а `.target` группирует units и задаёт точку
синхронизации загрузки или остановки. Target не является отдельным прикладным
процессом.

`default.target` — псевдоним стандартной цели загрузки. На рабочей Ubuntu это
`graphical.target`; она включает обычные системные службы через
`multi-user.target`. При выводе графа systemd использует каноническое имя, поэтому
псевдоним `default.target` не обязан отображаться отдельным узлом.

Зависимости активации и порядок запуска — разные отношения:

- `Wants=` и `Requires=` добавляют другой unit в транзакцию. `Wants=` является
  слабой зависимостью, а `Requires=` — более строгой;
- `After=` и `Before=` задают порядок, только если оба unit уже участвуют в
  транзакции. Сами по себе они другой unit не активируют;
- `WantedBy=` в секции `[Install]` сообщает `systemctl enable`, для какого target
  создать ссылку в каталоге `.wants/`.

Состояния `enabled` и `active` независимы. Первое описывает участие unit в
будущей загрузке, второе — его состояние сейчас. `active (exited)` не означает
ошибку: для `Type=oneshot` с `RemainAfterExit=on` команда уже может завершиться,
а unit остаётся логически активным.

Пакет PostgreSQL использует два уровня. `postgresql.service` — мета-unit для
всех кластеров, а `postgresql@18-main.service` — экземпляр шаблонного unit,
который управляет реальным кластером версии 18 с именем `main`.

#### Что я выполнил и подтвердил

- Определил `graphical.target` как стандартную загрузочную цель.
- Установил обратную цепочку зависимости:
  `postgresql.service -> multi-user.target -> graphical.target`.
- Подтвердил для `postgresql.service`: `enabled`, `active`, `SubState=exited`,
  `WantedBy=multi-user.target` и `Wants=postgresql@18-main.service`.
- Подтвердил для реального кластера `postgresql@18-main.service`:
  `active`, `SubState=running` и `PartOf=postgresql.service`.
- Увидел парную связь порядка: кластер имеет `Before=postgresql.service`, а
  мета-unit — `After=postgresql@18-main.service`.
- Ничего не запускал, не останавливал и не включал: граф исследован только
  читающими командами.

#### Прогноз и уточнение

Я правильно спрогнозировал `graphical.target`, а также наличие
`multi-user.target` и `graphical.target` над PostgreSQL. `default.target` не
появился отдельной строкой, потому что это псевдоним канонической цели.

Я предположил, что PostgreSQL будет `enabled`, но не `active`. Фактически
мета-unit был `active (exited)`, а кластер — `active (running)`. Слово `exited`
здесь описывает завершение процесса oneshot, а `active` — сохранённое systemd
состояние успешно активированного unit.

#### Ошибка с журналом

Сначала несколько результатов не сохранились, потому что журнал был частично
перезаписан. Недостающие данные добавлены через `>>`. Это повторно подтвердило
правило: `>` заменяет содержимое файла, а `>>` добавляет данные в конец.
Локальное доказательство хранится в игнорируемом Git файле
`uploads/systemd-dependencies.log`; проверенные результаты перечислены выше.

3. Почему `active (exited)` может быть корректным состоянием службы?

### 2026-09-19 — Жизненный цикл собственного systemd unit

#### Место темы и теория

До появления долгоживущего backend-процесса создан отдельный учебный
`lab-storage-training.service`. Он проверяет эксплуатационную механику, но не
выдаётся за готовую службу приложения: `ExecStart=/usr/bin/sleep infinity`
лишь предоставляет безопасный долгоживущий процесс.

Системные unit-файлы администратора размещаются в `/etc/systemd/system`.
`systemctl daemon-reload` перечитывает конфигурацию и перестраивает граф units,
но сам по себе не перезапускает службы. `enable` создаёт загрузочные ссылки, а
`start` активирует unit сейчас; `enable --now` выполняет обе операции.

В учебном unit использованы следующие решения:

- `Type=exec` позволяет считать запуск успешным после успешного выполнения
  `exec` и обнаруживать ошибки запуска программы или смены пользователя;
- `User=` и `Group=` запускают процесс с правами отдельной системной учётной
  записи вместо root;
- `WorkingDirectory=` задаёт каталог данных процесса;
- `Environment=ИМЯ=значение` передаёт переменную окружения;
- `Restart=on-failure` восстанавливает службу после аварийного завершения, но
  не отменяет осознанную команду `systemctl stop`;
- `RestartSec=` задерживает повторный запуск, а `TimeoutStopSec=` ограничивает
  ожидание штатной остановки.

При штатной остановке systemd сам отправляет сигнал процессам unit. Документация
прямо исключает такой результат из автоматического рестарта. SIGKILL извне —
аварийное завершение, поэтому оно подпадает под `Restart=on-failure`.

#### Что я выполнил и подтвердил

- Самостоятельно создал `/etc/systemd/system/lab-storage-training.service` и
  проверил его через `systemd-analyze verify`.
- Запустил процесс от пользователя и группы `lab-storage` с рабочим каталогом
  `/var/lib/lab-storage`; `ps` подтвердил владельца процесса.
- При обычном `systemctl stop` получил `inactive`, `Result=success`,
  `MainPID=0` и `NRestarts=0`.
- После принудительного SIGKILL systemd через заданную задержку восстановил
  службу: PID изменился с 358129 на 358148, а `NRestarts` вырос до 1.
- После опыта выполнил `disable --now`: загрузочная ссылка отсутствует,
  процесс пользователя `lab-storage` не остался запущенным.
- Подтвердил окружение двумя способами: свойство unit содержит
  `LAB_STORAGE_MODE=training`, и то же присваивание найдено в
  `/proc/PID/environ` реального процесса.

#### Ошибка и разбор

| Симптом | Причина | Исправление | Общее правило |
| --- | --- | --- | --- |
| `systemctl show` вывел пустое `Environment=` | Была записана строка `Environment=training`, хотя systemd ожидает присваивание переменной | Использовано `Environment=LAB_STORAGE_MODE=training`, затем выполнен `daemon-reload` и повторная проверка | В директиве `Environment=` всегда указывать `ИМЯ=значение`; проверять и конфигурацию systemd, и окружение процесса |

Учебный процесс не проверяет запуск Python backend, подключение к PostgreSQL,
health endpoint, миграции и корректное завершение запросов приложения. Поэтому
постоянный production-подобный `lab-storage.service` остаётся отдельной задачей
после появления долгоживущего backend-процесса.

### 2026-09-20 — Journald: авария, restart и постоянное хранение

#### Место темы и теория

`systemd-journald` собирает сообщения служб, самого service manager, ядра и
совместимых источников syslog. Journal хранит структурированные записи, а не
только текстовые строки. Среди полей есть сообщение, приоритет, идентификатор
загрузки, PID, UID и связь с unit.

`journalctl -u` выбирает не только сообщения, созданные процессами unit через
`_SYSTEMD_UNIT`, но и сообщения systemd о жизненном цикле этого unit. Поэтому
источник записи и объект события могут различаться. Например, сообщение
`Stopped ...` создал PID 1: у него `_SYSTEMD_UNIT=init.scope`, тогда как поле
`UNIT=lab-storage-training.service` указывает службу, которую остановил manager.

Ключ `-b` ограничивает выборку конкретной загрузкой, `--since` — временем,
`-p` — приоритетом, а `-o verbose` раскрывает структурированные поля. Поля с
начальным подчёркиванием добавляет сам journal и приложения не могут менять их
произвольно.

Временные journal-файлы находятся под `/run/log/journal` и не переживают
перезагрузку. Постоянные располагаются под `/var/log/journal`. Наличие старых
boot ID в `journalctl --list-boots` является фактическим доказательством, что
история действительно сохранилась между загрузками.

Journald ограничивает занимаемое место и ротирует активные файлы в архивные.
Параметры `SystemMaxUse`, `RuntimeMaxUse`, `MaxRetentionSec` и `MaxFileSec`
управляют объёмом и сроком хранения. `journalctl --disk-usage` только измеряет
место, тогда как `--vacuum-*` удаляет архивные данные и требует отдельного
осознанного решения.

#### Что я выполнил и подтвердил

- Ограничил выборку моментом начала опыта и unit
  `lab-storage-training.service`.
- Journal зафиксировал первоначальный запуск, завершение через SIGKILL со
  `status=9/KILL`, результат `signal`, запланированный restart со счётчиком 1,
  повторный запуск и финальную успешную остановку.
- Между аварией в 23:53:24 и повторным запуском в 23:53:26 прошли настроенные
  две секунды `RestartSec`.
- В подробной записи увидел `PRIORITY=6`, `_BOOT_ID`, данные PID 1,
  `JOB_TYPE=stop`, `UNIT=lab-storage-training.service` и текст `MESSAGE`.
- Подтвердил каталог `/var/log/journal` и историю пяти загрузок от `-4` до `0`;
  старые события действительно пережили перезагрузки.
- Постоянные и активные журналы занимали 268,5 МиБ. Очистку и принудительную
  ротацию не выполнял.
- После опыта учебная служба неактивна, не включена в автозагрузку, процесс
  `sleep` от пользователя `lab-storage` отсутствует.

#### Мой прогноз

Я правильно спрогнозировал, что запись об автоматическом рестарте сохранится
после последующей остановки службы. Также правильно определил
`/var/log/journal` как каталог постоянного хранения.

#### Важное уточнение

Нельзя требовать, чтобы каждая строка из `journalctl -u example.service`
содержала `_SYSTEMD_UNIT=example.service`. Сообщение мог создать systemd manager
о чужом unit. Для диагностики нужно совместно читать источник записи,
специализированное поле `UNIT`, `MESSAGE` и остальные поля события.

### 2026-09-21 — Ротация journald и первый Bash-сценарий

#### Место темы и теория

Journald пишет новые события в активные journal-файлы и после ротации превращает
их в архивные. `journalctl --vacuum-*` удаляет только архивы. Поэтому указанный
предел vacuum не гарантирует такой же итоговый результат `--disk-usage`: в него
также входят активные файлы, которые vacuum не удаляет.

`SystemMaxUse` ограничивает место журнала, а `SystemKeepFree` резервирует место
для остальных данных файловой системы; journald соблюдает более строгое из двух
ограничений. Для не переопределённых параметров systemd 259 рассчитывает 10% и
15% размера файловой системы соответственно, ограничивая каждое значение
сверху 4 ГиБ. На корневой файловой системе размером 203 ГиБ расчёт упирается в
этот предел 4 ГиБ, тогда как фактический journal занимал 268,5 МиБ.

Чтобы не удалять реальные диагностические данные, vacuum проверен на отдельной
копии архивного файла через `journalctl --directory=...`. Параметр `--directory`
перенаправляет операцию на указанный каталог, поэтому оригинальный journal не
был целью удаления.

Связная практика оформлена как Bash-сценарий в локальном `scratch/`, а не как
цепочка ручных команд. Для редактирования установлены Bash IDE 1.43.2,
ShellCheck 0.11.0 и shfmt 3.12.0. Рабочая последовательность:

1. `shfmt -w` приводит файл к единому формату;
2. `bash -n` проверяет синтаксис без выполнения;
3. ShellCheck выполняет статический анализ распространённых ошибок;
4. сценарий запускается через `bash` и проверяется по фактическому результату.

Ни один из этих инструментов не доказывает правильность намерения программы.
Формально допустимый Bash может выполнять не то, что ожидал автор, поэтому
runtime-проверка и валидация результата обязательны.

- `--vacuum-size=1` удалил только эту копию и сообщил об освобождении 8 МиБ.
- `test -f` вернул 0 для исходного файла в `/var/log/journal`; оригинал остался.

### Место темы в `lab-storage`

Модель данных задаёт словарь предметной области: какие сущности существуют, какие данные они
хранят и как связаны. В `lab-storage` верхний уровень — исследование `Study`, внутри него идут
сессии загрузки `Session`, а к каждой сессии относятся файлы `File`.

Python выбран основным языком приложения и автоматизации. Это позволяет глубоко изучать один
защищаемый на собеседовании язык и применять его сразу в трёх направлениях проекта: backend,
QA automation и DevOps-скрипты. Выбор не означает, что Go хуже; он исключён из текущего учебного
контура, чтобы не распылять время.

#### Класс, экземпляр и атрибут

**Класс** создаёт новый тип объектов и описывает общие для них данные и поведение. **Экземпляр** —
конкретный объект этого класса: например, `Study` является классом, а созданное исследование с
`id=1` — его экземпляром. **Атрибут** — имя внутри объекта, доступное через точку, например
`study.name`.

Класс можно представить как описание формы данных, а экземпляр — как отдельную заполненную форму.
Например, класс `Study` задаёт поля всех исследований, но каждый созданный объект `Study` хранит
собственные значения этих полей.

Метод — функция, связанная с объектом. При вызове `object.method()` Python автоматически передаёт
сам объект первым аргументом метода. По соглашению этот параметр называется `self`; специальным
ключевым словом он не является. Вызов `study.method()` по механике передачи объекта соответствует
вызову функции класса с явным первым аргументом: `Study.method(study)`.

#### Что делает `@dataclass`

`@dataclass` — декоратор класса. Декоратор получает уже созданный объект класса и возвращает
обработанный класс. Модуль стандартной библиотеки `dataclasses` по аннотированным полям генерирует
служебные методы, в том числе `__init__` для начальной инициализации и `__repr__` для отладочного
представления.

`dataclass` сокращает шаблонный код модели, но не превращает аннотации в runtime-проверки. Запись
`id: int` сообщает ожидаемый тип человеку и статическому анализатору; обычный вызов Python сам по
себе не обязан отклонить строку вместо числа.

#### Имена, ссылки и изменяемые объекты

В Python присваивание не копирует объект: оно связывает имя с объектом. Несколько имён могут
ссылаться на один изменяемый список, поэтому изменение через одно имя будет видно через другое.
Это называется **aliasing**, или наличие нескольких ссылок на один объект.

Например, после `first = []` и `second = first` оба имени связаны с одним списком. Поэтому
`second.append(1)` меняет тот же объект, который виден через `first`; присваивание само по себе
не создало второй список.

Изменяемый список нельзя использовать как один общий объект по умолчанию для всех экземпляров.
`field(default_factory=list)` хранит ссылку на фабрику и вызывает `list()` при создании каждого
нового экземпляра. Поэтому у двух исследований будут разные списки `sessions`. Круглые скобки после
`list` здесь отсутствуют намеренно: передаётся функция, а не результат её немедленного вызова.

#### Дерево в памяти и внешние ключи

В памяти удобно собрать дерево: `Study.sessions` содержит объекты `Session`, а `Session.files` —
объекты `File`. Метод `append` добавляет в список ссылку на уже созданный объект. Такое дерево удобно
печатать, отдавать в генератор и обходить вложенными циклами.

Для постоянного хранения используется другая форма связи: дочерняя запись хранит ID родителя.
`Session.study_id` и `File.session_id` — будущие внешние ключи базы. Это похоже на номер записи
в каталоге: ребёнок хранит номер родителя, а не полную копию всех его данных.

Обе формы намеренно присутствуют одновременно:

- вложенные списки дают удобную объектную структуру в оперативной памяти;
- ID позволяют выразить связь в реляционной базе и передавать идентификаторы через API;
- согласованность этих двух представлений должна проверяться тестами и позже обеспечиваться слоем
  работы с базой.

#### Реализация раздела

- [`models.py`](models.py) — Python-модели, фабрики значений по умолчанию и аннотации связей.
- [`main.py`](main.py) — сборка и вложенный обход дерева `Study -> Session -> File`.
- [`generator.py`](generator.py) — создание синтетического дерева без реальных лабораторных данных.

#### Формулировки для собеседования

- Класс определяет новый тип, экземпляр хранит состояние конкретного объекта, а `self` — явный
  первый параметр метода, который Python подставляет при вызове через экземпляр.
- `dataclass` генерирует типовой код модели по аннотированным полям, но не выполняет runtime-проверку
  указанных типов.
- Присваивание в Python связывает имя с объектом, а не копирует данные; поэтому изменяемые объекты
  требуют внимания к aliasing.
- `default_factory` создаёт новое изменяемое значение для каждого экземпляра и предотвращает
  совместное использование одного списка.
- Вложенность объектов удобна в памяти, а внешний ключ хранит устойчивую связь между строками в БД.

## Python и автоматизация тестирования

### Место темы в `lab-storage`

Python выполняет две роли: на нём будет написан backend, и им же автоматизируются генерация
синтетических данных, проверки и эксплуатационные задачи. pytest проверяет наблюдаемое поведение,
mypy сопоставляет код с аннотациями типов, а Ruff проверяет стиль и набор статических правил. Эти
инструменты отвечают на разные вопросы и не заменяют друг друга.

#### Модуль и точка входа

Каждый файл `.py` является модулем. При импорте Python создаёт объект модуля и выполняет его код
верхнего уровня. Поэтому исполняемые действия на верхнем уровне могут неожиданно запуститься и в
тестах, которые импортируют функцию.

`__name__` — специальное имя модуля. У непосредственно запущенного файла оно равно `"__main__"`,
а у импортированного — имени модуля. Условие `if __name__ == "__main__":` отделяет определение
функций от запуска программы: импорт предоставляет функции, но не стартует демонстрационный сценарий.

Импорт не копирует текст одного файла в другой. Python загружает и выполняет модуль как объект
времени выполнения, после чего его имена доступны через пространство имён.

#### Функция, результат и раннее завершение

Функция создаётся конструкцией `def`. `return value` немедленно завершает текущий вызов и возвращает
значение. Если выполнение дошло до конца без `return`, результатом будет `None` — отдельный объект,
обозначающий отсутствие значения.

Guard clause — ранняя проверка недопустимого случая. В генераторе каждый отрицательный аргумент
проверяется отдельным `if`, после чего `raise ValueError(...)` немедленно прерывает функцию.
`ValueError` применяется, когда тип аргумента допустим, но само значение не входит в разрешённый
диапазон. После всех guard clauses основной путь можно писать линейно, без большого `else`.

Порядок проверок наблюдаем извне: если одновременно неверны несколько аргументов, вызывающий код
получит исключение от первого сработавшего guard. Поэтому негативный unit-тест меняет одну причину,
иначе он может проверить не тот контракт.

#### Время и фабрики значений

`datetime` может быть timezone-aware — содержать информацию о часовом поясе — или naive, без неё.
Для меток событий проект использует UTC-aware значение. Суффикс `+00:00` означает нулевое смещение
от UTC и делает временную шкалу однозначной между машинами.

В `field(default_factory=utc_now)` передаётся сам объект-функция. `dataclass` вызывает его отдельно
при создании каждого экземпляра. Если вместо этого вычислить время один раз при объявлении класса,
несколько последующих объектов смогут получить одно старое значение.

#### Синтетические и воспроизводимые данные

Генератор создаёт только вымышленные исследования, пользователей и имена файлов. Это позволяет
разрабатывать публичный проект без утечки лабораторных или персональных данных.

Псевдослучайный генератор по начальному состоянию `seed` создаёт воспроизводимую последовательность:
в одной версии реализации одинаковый seed и одинаковый порядок вызовов дают одинаковые выбранные
значения. Локальный объект `Random(seed)` изолирует генератор от глобального состояния модуля
`random`, поэтому чужой вызов не меняет тестовый сценарий. Такая случайность подходит для синтетики
и тестов, но не для паролей, токенов или криптографических ключей.

#### Как устроен unit-тест

Unit-тест проверяет небольшую единицу поведения в изоляции от сети и production-базы. В pytest тест —
обычная функция с именем `test_...`. Внутри используется `assert`: если выражение ложно, тест падает,
а pytest показывает значения частей выражения.

Полезная мысленная структура теста:

1. **Arrange** — подготовить входные данные и ожидаемый результат.
2. **Act** — вызвать проверяемое действие.
3. **Assert** — сравнить наблюдаемый результат с контрактом.

Для исключений применяется `pytest.raises`. Контекстный менеджер подтверждает тип исключения, а
`match` проверяет его сообщение регулярным выражением. Если исключения не было или оно другого типа,
тест падает.

Fixture — подготовленный pytest ресурс, который тест запрашивает аргументом функции. `tmp_path`
передаёт отдельный временный каталог в виде `Path`; тест не выбирает глобальное имя и не оставляет
артефакт в репозитории.

Зелёный тест доказывает только записанные утверждения. Если требование о размере файла отсутствует
в `assert`, тест ничего о размере не подтверждает. Поэтому тестирование включает не только запуск,
но и анализ полноты проверяемого контракта.

#### Границы, классы эквивалентности и уникальность

Класс эквивалентности — группа входов, для которых ожидается одинаковое поведение. Для количества
файлов значения можно разделить как минимум на отрицательные, ноль и положительные. `-1` должен
вызывать ошибку, `0` создавать допустимую пустую коллекцию, положительное число — заданное количество.

Проверка количества и проверка уникальности независимы. Список `[1, 1, 1, 1]` имеет длину четыре,
но множество из него — длину один. Поэтому сравнение `len(ids)` с ожидаемым количеством проверяет
число объектов, а сравнение `len(ids) == len(set(ids))` — отсутствие повторяющихся ID.

List comprehension создаёт список из элементов и выражений цикла. Вложенная форма для файлов
эквивалентна двум циклам: внешний перебирает сессии, внутренний — файлы текущей сессии.

#### Файлы и управление ресурсом

`Path` представляет путь как объект и позволяет соединять компоненты оператором `/`. Само создание
`Path` не создаёт файл. `Path.open("w", encoding="utf-8")` открывает текстовый поток на запись;
режим `w` создаёт файл или обнуляет существующий, а `a` дописывает в конец.

Оператор `with` работает через протокол контекстного менеджера. При входе приобретается ресурс, а
при выходе вызывается завершающая операция и при нормальном выполнении, и при исключении. Для файла
это гарантированное закрытие, встроенное в структуру блока; вручную дублировать `close()` во всех
ветках выполнения не нужно.

#### Типы и инструменты качества

Python динамически типизирован: объект несёт тип во время выполнения, а имя можно позже связать с
объектом другого типа. Аннотации описывают ожидаемый контракт, но интерпретатор обычно не превращает
их в автоматические проверки вызова.

mypy — статический анализатор: он читает исходный код, сопоставляет операции с аннотациями и не
запускает программу. Строгий режим усиливает набор проверок, но mypy не заменяет runtime-валидацию
входных данных и тесты поведения.

Ruff ищет выбранные классы ошибок и проверяет форматирование. `pip check` проверяет, совместимы ли
установленные пакеты по объявленным зависимостям. Разделение файлов зависимостей не даёт pytest и
линтерам без необходимости попасть в production-окружение:

- `requirements.txt` — пакеты, нужные работающему приложению;
- `requirements-dev.txt` — runtime-набор через `-r` плюс инструменты разработки.

Стандартная библиотека (`pathlib`, `random`, `datetime`) поставляется вместе с Python и в список
сторонних зависимостей не записывается.

## PostgreSQL и SQL

### Место PostgreSQL в `lab-storage`

PostgreSQL хранит метаданные: исследования, сессии загрузки и описания файлов. Сами
большие файлы будут лежать на диске. Такое разделение позволяет реляционной базе проверять
связи и искать записи, не превращая её в хранилище многогигабайтных бинарных объектов.

Реляционная модель представляет данные в виде таблиц. Строка — один экземпляр сущности, столбец —
один её атрибут. В памяти Python связь `Study -> Session -> File` можно собрать как вложенное дерево. В базе
дочерняя строка хранит не весь объект родителя, а его ID: по этому номеру PostgreSQL находит запись
родителя в центральной таблице.

#### Ограничения как инварианты

Ограничение, или constraint, — правило, которое PostgreSQL проверяет при изменении данных. Это инвариант:
условие, которое должно оставаться истинным для любого допустимого состояния базы.

Валидация в Python всё равно нужна для хорошего ответа API, но она не заменяет ограничения схемы. В базу
может писать не только API, но и миграция, тест, `psql` или администратор. Поэтому недостаточно
проверить данные в одной Python-функции: инвариант нужно защитить и на границе самой базы.

| Ограничение | Что гарантирует | Пример в проекте | SQLSTATE нарушения |
| --- | --- | --- | --- |
| `NOT NULL` | Значение обязательно | `studies.name` | `23502` |
| `PRIMARY KEY` | Строка имеет уникальный непустой ID | `studies.id` | `23505` для дубликата |
| `FOREIGN KEY` | У дочерней строки есть существующий родитель | `sessions.study_id` | `23503` |
| `CHECK` | Логическое условие не ложно | `size_bytes >= 0` | `23514` |

SQL использует трёхзначную логику: `TRUE`, `FALSE` и `UNKNOWN`. Для `NULL` выражение `size_bytes >= 0` даёт
`UNKNOWN`, а `CHECK` отклоняет только `FALSE`. Поэтому `CHECK (size_bytes >= 0)` и `NOT NULL` решают разные задачи и нужны
одновременно.

#### ID, identity и `RETURNING`

`GENERATED ALWAYS AS IDENTITY` поручает PostgreSQL генерировать ID. При параллельных вставках последовательность
атомарно выдаёт разные значения. Но эти значения не обещают быть без пропусков: откат транзакции не
возвращает уже выданное значение обратно. ID — это идентификатор, а не порядковый номер без дыр.

`INSERT ... RETURNING id` возвращает ID строки, созданной этой же командой. Отдельный `SELECT max(id)` не равноценен:
между `INSERT` и `SELECT` другой клиент может вставить новую строку, и первый клиент получит чужой ID.

#### Транзакции в негативных проверках

Транзакция группирует изменения в операцию «всё или ничего». `COMMIT` фиксирует результат, `ROLLBACK`
отменяет изменения. После ошибки внутри транзакции PostgreSQL считает её аварийно завершённой; вернуть
управление можно полным `ROLLBACK` или откатом к заранее созданной точке сохранения.

В [`sql/check_constraints.sql`](sql/check_constraints.sql) каждая намеренно неверная вставка запускается в отдельной транзакции.
`\set ON_ERROR_STOP off` временно говорит клиенту `psql` продолжить чтение файла после ожидаемой ошибки; сами
ограничения сервера эта метакоманда не отключает.

#### Лексические правила SQL

- `;` завершает SQL-команду.
- `'text'` — строковая константа.
- `"name"` — кавыченный SQL-идентификатор, например точное имя столбца.
- В выражении `source_column AS output_label` слева находится источник значения,
  а справа создаётся временная метка столбца результата. `AS` не изменяет схему
  и не требует, чтобы `output_label` уже существовал в таблице.
- Скалярный подзапрос — `SELECT` в скобках, возвращающий один столбец и не более одной строки. Его
  результат можно использовать там, где ожидается одно значение.

### 2026-08-03 — Нормализация и аномалия обновления

#### Термины и теория

Нормализация организует отношения так, чтобы самостоятельный факт хранился в
одном подходящем месте. Функциональная зависимость `X -> Y` означает, что одно
значение `X` однозначно определяет значение `Y`. Кандидатный ключ — минимальный
набор атрибутов, определяющий строку; один из кандидатных ключей выбирается как
первичный.

- В первой нормальной форме одна строка представляет один экземпляр сущности,
  а повторяющиеся наборы не раскладываются по столбцам вида `file_1`, `file_2`.
- Во второй нормальной форме неключевой атрибут зависит от всего составного
  ключа, а не только от его части. В текущих таблицах одиночные первичные ключи
  `id` исключают частичную зависимость от части первичного ключа.
- В практической модели третьей нормальной формы неключевые атрибуты зависят от
  ключа своей сущности, а не от другого неключевого атрибута.

Денормализация допустима как осознанный компромисс ради измеренной
производительности, но создаёт обязанность поддерживать копии данных в
согласованном состоянии.

#### Место темы в `lab-storage`

Цепочка `studies -> sessions -> files` уже разделяет разные сущности и хранит
связи через внешние ключи. Поле `sessions.uploader` требует уточнения смысла.
Историческая текстовая подпись может оставаться текстом, но пользователь с
аутентификацией, ролью и аудитом является отдельной сущностью. Для него нужна
таблица `users`, а сессия должна ссылаться на неё через `uploader_id`.

Постоянная схема пока не изменена: поля пользователя будут определены целиком
перед ORM-моделями и миграциями. Это не позволяет преждевременно закрепить
неполный контракт аутентификации.

#### Что я реализовал

- Создал [`sql/normalization.sql`](sql/normalization.sql) с денормализованной и
  нормализованной временными моделями.
- В первой модели дважды сохранил username и роль одного загрузившего
  пользователя непосредственно в строках сессий.
- Изменил роль только в первой строке и получил противоречивые данные.
- Во второй модели вынес username и роль в `normalized_users`, а две сессии
  связал с пользователем через один `uploader_id`.
- Получил ID пользователя через `RETURNING ... \gset`, изменил одну строку
  пользователя и собрал результат через `JOIN`.

#### Проверенный результат

- Денормализованный вывод показал `admin` для `Session A` и `researcher` для
  `Session B`, хотя username у строк совпадал.
- Нормализованный вывод показал `admin` для обеих сессий, потому что роль
  хранится в единственной строке пользователя.
- В итоговом `SELECT` явно выбраны `note`, `username` и `role`; сортировка идёт
  по ID сессии.
- Временные таблицы не изменили постоянную схему базы.

#### Что я понял

- В отдельную таблицу выносятся не просто «независимые параметры», а факты,
  относящиеся к другой сущности и зависящие от её ключа.
- `note` зависит от сессии и остаётся в `sessions`; `username` и `role` зависят
  от пользователя и хранятся в `users`.
- Нормализация устраняет аномалию обновления: роль меняется в одном месте, а
  связанные сессии получают актуальное значение через `JOIN`.

### 2026-08-03 — Действия внешнего ключа при удалении

#### Термины и поведение

Referential action, или действие внешнего ключа, определяет судьбу дочерних
строк при удалении либо изменении ключа родителя. Действие записывается в
определении внешнего ключа ребёнка, хотя запускает его операция над родителем.

- `NO ACTION` используется по умолчанию и не позволяет оставить нарушенную
  ссылку. Проверку можно отложить, если ограничение допускает отложенную
  проверку.
- `RESTRICT` также запрещает удаление родителя с детьми, но проверяется сразу и
  не может быть отложено.
- `CASCADE` удаляет связанные дочерние строки в той же транзакции.
- `SET NULL` оставляет ребёнка и обнуляет внешний ключ, поэтому несовместим по
  смыслу с обязательной ссылкой `NOT NULL`.
- `SET DEFAULT` подставляет значение по умолчанию, которое всё равно обязано
  удовлетворять внешнему ключу.

Каскад может пройти несколько уровней. Если `sessions.study_id` и
`files.session_id` имеют `ON DELETE CASCADE`, удаление исследования удаляет его
сессии, а удаление этих сессий — их файлы. Все изменения принадлежат одной
транзакции и возвращаются после `ROLLBACK`.

#### Инженерное решение для `lab-storage`

В постоянной схеме пока сохранено стандартное `NO ACTION`. Метаданные файла
находятся в PostgreSQL, а сам файл будет лежать на диске. Каскад базы не удаляет
физический файл и не может атомарно откатить операцию файловой системы. Поэтому
постоянное поведение удаления будет выбрано вместе со сценарием очистки диска,
а не только ради удобства удаления строк.

#### Что я реализовал

- Создал [`sql/on_delete.sql`](sql/on_delete.sql) с временной цепочкой
  `cascade_studies -> cascade_sessions -> cascade_files`.
- Задал `ON DELETE CASCADE` на обоих внешних ключах дочерних таблиц.
- Создал одно исследование, две сессии и три файла, получая identity-ID через
  `RETURNING ... \gset`, а не фиксируя значения вручную.
- Удалил только исследование внутри транзакции и проверил автоматическое
  удаление обоих уровней детей.
- Выполнил `ROLLBACK` и проверил восстановление всего дерева.

#### Ошибки и разбор

| Симптом | Причина | Исправление | Общее правило |
| --- | --- | --- | --- |
| Первый счётчик показывал два исследования вместо одного | После `RETURNING id AS study_id` стоял `;`, а следующая `\gset` повторно отправила тот же `INSERT` серверу | Убрал `;` перед `\gset` | При сохранении результата в переменные `psql` метакоманда `\gset` отправляет запрос и заменяет завершающую точку с запятой |

#### Проверенный результат

- До удаления счётчики исследований, сессий и файлов равнялись `1/2/3`.
- Один `DELETE` исследования вернул `DELETE 1`; внутри транзакции все три
  счётчика стали равны нулю.
- После `ROLLBACK` счётчики восстановились до `1/2/3`, включая строки,
  удалённые PostgreSQL каскадно.
- Постоянные таблицы `studies`, `sessions` и `files` сохранили количества
  `1/2/3`.
- Временные таблицы исчезли после завершения подключения `psql`.

#### Что я понял

- Для многоуровневого каскада действие должно быть допустимо на каждом звене
  цепочки внешних ключей.
- Если удаление исследования каскадно пытается удалить сессии, но файлы
  защищают эти сессии стандартным `NO ACTION`, PostgreSQL отклонит всю исходную
  команду `DELETE`.
- Ошибка на нижнем уровне не оставит дерево частично удалённым: изменения одной
  SQL-команды атомарны.

#### Вопросы для самопроверки

1. На каком внешнем ключе нужно писать `ON DELETE CASCADE`, чтобы удаление
   исследования удаляло его сессии?
2. Почему каскадное удаление строк `files` не решает удаление настоящих файлов
   с диска?

- Для созданной пустой сессии `INNER JOIN` вернул ноль строк.
- `LEFT JOIN` вернул одну строку с данными сессии и значениями `[NULL]` в
  `file_id` и `file_name`.
- Агрегатный запрос вернул счётчики `2/2` и `1/1` для сессий с файлами, а для
  пустой сессии — `joined_row_count = 1` и `file_count = 0`.
- `HAVING` отфильтровал уже сформированные группы и вернул только первую сессию
  со значением `file_count = 2`.
- После `ROLLBACK` запрос `count(*)` подтвердил отсутствие тестовой сессии.

#### Что я понял

- `LEFT JOIN` сохраняет строки таблицы, написанной слева от слов `LEFT JOIN`.
- В конструкции `studies LEFT JOIN sessions` гарантированно сохраняются
  исследования, а не каждая сессия.
- Последующий обычный `JOIN files` требует совпавший файл и поэтому способен снова
  удалить пустую сессию. Для сохранения всех сессий нужна конструкция
  `sessions LEFT JOIN files`.
- `count(*)` считает все строки группы, включая созданную `LEFT JOIN` строку с
  отсутствующим файлом.
- `count(f.id)` считает только ненулевые значения `f.id`; у пустой сессии одна
  результирующая строка, но `f.id` в ней равен `NULL`, поэтому количество файлов
  равно нулю.
- `WHERE` фильтрует отдельные строки до `GROUP BY`, когда агрегатные значения ещё
  не вычислены.
- `HAVING` фильтрует уже сформированные группы и поэтому может проверять условие
  вида `count(f.id) >= 2`.

### 2026-08-02 — Ограничение `UNIQUE`

#### Термины и поведение

`UNIQUE` — ограничение целостности, запрещающее повторение значения или
комбинации значений в разных строках. В отличие от `PRIMARY KEY`, оно защищает
дополнительный бизнес-ключ: у таблицы может быть несколько ограничений
`UNIQUE`, но только один первичный ключ. В PostgreSQL ограничение автоматически
создаёт уникальный B-tree индекс.

Столбцовая запись `username text NOT NULL UNIQUE` одновременно задаёт тип,
обязательность значения и его уникальность. Табличная форма
`UNIQUE (first_column, second_column)` проверяет уникальность всей пары, а не
каждого столбца отдельно. По умолчанию два `NULL` не считаются равными для
`UNIQUE`; сочетание с `NOT NULL` исключает эту неоднозначность для обязательного
бизнес-ключа.

Нарушение уникальности имеет SQLSTATE `23505`. Проверка в Python полезна для
понятного ответа API, но только ограничение базы защищает правило от всех
клиентов и одновременных операций.

#### Принятое решение

В постоянную схему `studies`, `sessions` и `files` ограничение пока не добавлено.
Уникальность названия исследования или имени файла внутри сессии ещё не
подтверждена требованиями лаборатории. Ограничение, не отражающее реальное
бизнес-правило, способно запретить допустимые данные. Поведение проверено на
временной таблице будущих пользователей, где уникальное имя входа является
понятным примером инварианта.

#### Что я реализовал

- Создал [`sql/unique_constraint.sql`](sql/unique_constraint.sql) с временной
  таблицей `synthetic_users`.
- Сделал `username` обязательным и уникальным.
- Временно отключил остановку `psql` только вокруг намеренной повторной
  вставки, не отключая само ограничение PostgreSQL.
- После ошибки вставил другое имя и вывел итоговые строки по ID.

### 2026-08-04 — Атомарность и согласованность транзакций

#### Термины и теория

Транзакция объединяет несколько SQL-команд в одну логическую операцию.
`BEGIN` открывает явную транзакцию, `COMMIT` фиксирует все её изменения, а
`ROLLBACK` отменяет их. Без явного `BEGIN` каждая команда выполняется в своей
неявной транзакции.

ACID объединяет четыре свойства:

- atomicity — все изменения транзакции фиксируются вместе либо вместе
  отменяются;
- consistency — зафиксированное состояние удовлетворяет ограничениям и
  известным бизнес-инвариантам;
- isolation — параллельные транзакции наблюдают друг друга по правилам
  выбранного уровня изоляции;
- durability — подтверждённый `COMMIT` должен пережить завершение клиента и
  сбой процесса.

Ошибка SQL внутри явной транзакции переводит её в аварийное состояние.
Последующие обычные команды получают SQLSTATE `25P02`, пока клиент не выполнит
`ROLLBACK`. Метакоманда `psql` `ON_ERROR_STOP` управляет чтением файла клиентом,
но не восстанавливает транзакцию на сервере.

#### Что я реализовал

- Создал [`sql/acid_atomicity.sql`](sql/acid_atomicity.sql) с временными
  таблицами сессий и файлов.
- В первой транзакции успешно создал сессию, затем намеренно нарушил
  `CHECK (size_bytes >= 0)` при вставке файла.
- После ошибки выполнил запрос в аварийной транзакции, сделал `ROLLBACK` и
  проверил отсутствие ранее созданной сессии.
- Во второй транзакции создал допустимую сессию и файл, выполнил `COMMIT` и
  подтвердил связь строк через `JOIN`.

#### Ошибки и разбор

| Симптом | Причина | Исправление | Общее правило |
| --- | --- | --- | --- |

### 2026-08-11 — Изоляция, MVCC и снимки данных

#### Термины и теория

Изоляция определяет видимость изменений между параллельными транзакциями.
PostgreSQL использует MVCC: вместо обязательной блокировки читателя он выбирает
версию строки, видимую текущему снимку данных.

- Dirty read — чтение ещё не зафиксированных данных другой транзакции.
  PostgreSQL его не допускает.
- Non-repeatable read — повторное чтение строки внутри одной транзакции даёт
  другое подтверждённое значение.
- Phantom read — повторный запрос по условию получает новые подходящие строки.

В `READ COMMITTED` каждая SQL-команда получает новый снимок. В
`REPEATABLE READ` снимок сохраняется для транзакции после первого обычного
запроса, поэтому более поздние коммиты других клиентов внутри неё не видны.
`SERIALIZABLE` дополнительно требует результата, эквивалентного некоторому
последовательному порядку транзакций, и может вернуть `40001`, после которого
приложение повторяет транзакцию целиком.

#### Что я проверил

- Открыл два независимых подключения `psql` к `lab_storage` и использовал
  общую синтетическую таблицу `isolation_demo`.
- В `READ COMMITTED` первое подключение читало `'1'`, пока второе изменило
  значение на `'2'`, но ещё не выполнило `COMMIT`.
- До коммита второго подключения первое снова увидело `'1'`: грязного чтения
  не произошло.
- После коммита вторым подключением следующий `SELECT` первой транзакции увидел
  `'2'`: подтверждено неповторяемое чтение на уровне `READ COMMITTED`.
- В `REPEATABLE READ` первое подключение дважды увидело `'1'`, хотя между
  чтениями второе подключение зафиксировало `'2'`.
- После `COMMIT` первого подключения новый запрос увидел `'2'`, потому что
  прежний снимок завершился вместе с транзакцией.

#### Что я понял

- Уровень изоляции управляет видимостью конкурентных изменений, а не просто
  включает общую «защиту транзакции».
- В `READ COMMITTED` каждый запрос получает новый снимок и поэтому после чужого
  `COMMIT` может увидеть новое значение внутри прежней транзакции.
- В `REPEATABLE READ` запросы одной транзакции используют сохранённый снимок;
  чужое подтверждённое изменение становится видимым только после завершения
  этой транзакции и создания нового снимка.

#### Приглашения `psql`

- `=>` — клиент готов к новой команде вне транзакции;
- `->` — текущая команда не завершена;
- `=*>` — открыта нормальная транзакция;
- `-*>` — внутри транзакции ожидается продолжение команды;
- `=!>` — транзакция аварийная и требует `ROLLBACK`.

Метакоманда `\r` очищает незавершённый SQL-буфер, но не восстанавливает
аварийную транзакцию.

### 2026-08-14 — Первый индекс и чтение `EXPLAIN`

#### Термины и теория

Индекс — отдельная структура данных, связывающая индексируемые значения с
расположением строк таблицы. Индекс не заменяет таблицу и не гарантирует, что
планировщик применит его: PostgreSQL оценивает допустимые планы и выбирает план
с наименьшей расчётной стоимостью.

`CREATE INDEX` без секции `USING` создаёт B-tree индекс. Он подходит, в
частности, для сравнений `=`, `<`, `<=`, `>=` и `>`. Первичный ключ и
ограничение `UNIQUE` создают индексы автоматически, а объявление внешнего ключа
не создаёт индекс на ссылающемся столбце.

`EXPLAIN` показывает расчётный план. `EXPLAIN (ANALYZE, BUFFERS)` действительно
выполняет запрос и дополняет оценки фактическими строками, временем и работой с
буферами. Самостоятельная команда `ANALYZE table_name` выполняет другую задачу:
собирает статистику, по которой планировщик оценивает распределение данных.

#### Что я реализовал и проверил

- Создал [`sql/index_explain.sql`](sql/index_explain.sql) с временной таблицей
  `file_search_demo`.
- Через `generate_series(1, 50000)` и `INSERT ... SELECT` создал 50 000
  синтетических строк без ручного перечисления `VALUES`.
- Выражением `(n % 100) + 1` распределил строки между 100 значениями
  `session_id`: каждое значение встречается ровно 500 раз.
- Подтвердил агрегатами 50 000 строк, 100 разных `session_id` и диапазон от 1
  до 100.
- До индекса поиск `session_id = 42` использовал `Seq Scan`: вернул 500 строк
  и отфильтровал остальные 49 500.
- Создал B-tree индекс `file_search_demo_session_id_idx` на `session_id` и
  повторил тот же запрос без изменения его условия или выходных столбцов.
- После индекса план сменился на `Bitmap Index Scan`, передающий найденные
  расположения в `Bitmap Heap Scan`. Запрос снова вернул 500 строк.
- При уже существующем индексе выполнил запрос `session_id >= 1`, которому

В проверенном запуске расчётная полная стоимость снизилась с `1042.00` до
`454.49`, а полное время выполнения — примерно с `1.289 ms` до `0.247 ms`.
Эти конкретные значения зависят от среды и состояния кэша; инженерный вывод
основан прежде всего на смене способа доступа и уменьшении объёма поиска, а не
на гарантии такого же времени в каждом запуске.

#### Что я понял

- `Seq Scan` — не вручную включённый режим, а выбранный планировщиком узел
  последовательного чтения.
- До индекса PostgreSQL проверил все 50 000 строк, потому что другого способа

- Индекс изменил способ поиска, но не условие `WHERE`, поэтому оба плана вернули

- Bitmap-план читается снизу вверх: индексный узел находит расположения, затем
  heap-узел читает соответствующие строки основной таблицы.
- Наличие подходящего индекса не обязывает PostgreSQL использовать его. Когда
  условию соответствовала вся таблица, последовательное чтение было дешевле
  множества переходов от индекса к строкам таблицы.

## SQLAlchemy ORM

### Место темы в `lab-storage`

SQLAlchemy ORM связывает объектную модель Python с реляционной схемой PostgreSQL. SQL остаётся
основой хранения данных, а ORM добавляет типизированные Python-классы, через которые backend будет
создавать запросы и преобразовывать строки таблиц в объекты. Первые отображения охватывают таблицы
`studies`, `sessions` и `files`; подключения к PostgreSQL и выполнения запросов на этом шаге ещё нет.

#### Декларативная модель и метаданные

`DeclarativeBase` служит общей базой для ORM-классов. При объявлении подкласса SQLAlchemy создаёт
объект `Table` и сохраняет его в общей коллекции `Base.metadata`. Упрощённая структура выглядит так:

```text
Base
└── MetaData
    └── Table "studies"
        ├── Column "id"
        ├── Column "name"
        ├── Column "description"
        └── Column "created_at"
```

`__tablename__` задаёт точное имя SQL-таблицы. Аннотация `Mapped[T]` обозначает атрибут,
отображённый на столбец, а `mapped_column()` уточняет SQL-тип, первичный ключ, генерацию значения и
серверное значение по умолчанию. Неопциональная аннотация, например `Mapped[str]`, соответствует
запрету `NULL`; для допуска `NULL` тип должен включать `None`.

`Identity(always=True)` описывает `GENERATED ALWAYS AS IDENTITY`. Серверное значение по умолчанию
для `created_at` хранится в метаданных столбца и будет вычисляться СУБД при вставке, если приложение
не передало собственное значение. `DateTime(timezone=True)` описывает тип даты и времени с часовым
поясом.

Метаданные являются обычными Python-объектами, поэтому их можно проверить без соединения с базой.
`table.columns["id"]` возвращает объект `Column`: его свойства `primary_key`, `nullable`, `identity`,
`type` и `server_default` отражают объявленный контракт столбца.

Проверка `assert identity is not None` одновременно подтверждает контракт во время теста и сужает
тип для mypy: ниже анализатор уже разрешает доступ к `identity.always`. По той же причине
`isinstance(created_at_column.type, DateTime)` выполняется до обращения к свойству `timezone`.

#### Внешний ключ и объектная связь

`ForeignKey` и `relationship()` решают разные задачи. Внешний ключ описывает ограничение схемы:
значение дочернего столбца должно ссылаться на существующую строку родительской таблицы.
`relationship()` создаёт Python-навигацию между ORM-объектами и сам по себе не является столбцом.

Для связи один-ко-многим родительская сторона содержит коллекцию, а дочерняя — один объект:

```text
StudyORM.sessions: list[SessionORM]  <->  SessionORM.study: StudyORM
SessionORM.files: list[FileORM]      <->  FileORM.session: SessionORM
```

Параметр `back_populates` на каждой стороне называет противоположный атрибут и сообщает SQLAlchemy,
что это два направления одной связи. Поэтому добавление объекта в `study.sessions` синхронизирует
`session.study` в памяти. Аннотация должна отражать кардинальность точно: SQLAlchemy может определить
направление связи во время выполнения по внешнему ключу, но mypy опирается на записанный тип.

`studies.id` где-то существует в таблице `sessions`: нужно доказать, что она назначена именно
`study_id`.

### 2026-09-07 — Первый запуск через Session: COMMIT и ROLLBACK

#### Место темы и принцип работы

После проверки метаданных следующий шаг — выполнить операции с настоящей PostgreSQL через ORM.
`Session.add()` ставит новый объект в очередь на вставку, `flush()` отправляет изменения внутри
текущей транзакции, а `commit()` фиксирует её. Поэтому получение ID после `flush()` само по себе
не доказывает фиксацию строки.

`with Session(engine)` отвечает за закрытие рабочей области ORM. Дополнительный контекст
`session.begin()` задаёт автоматический commit при успешном выходе и rollback при исключении.
`Session.get()` позволяет получить объект по первичному ключу; если строки нет, результат — `None`.

Отсутствие явного `session.begin()` не означает отсутствие транзакции: по умолчанию действует
`autobegin` — автоматическое начало транзакционной работы. В этом примере `flush()` выполняет
вставку внутри транзакции. Если её не зафиксировать, закрытие `Session` откатит изменения.

#### Что я реализовал

- Добавил `psycopg[binary]==3.3.5` в [`requirements.txt`](requirements.txt). В окружении проверены
  `psycopg` и `psycopg-binary` версии `3.3.5`, SQLAlchemy остался на `2.0.52`.
- Создал [`database.py`](database.py) с локальным подключением к `lab_storage` и выводом SQL через
  `echo=True`.
- Написал [`orm_session_demo.py`](orm_session_demo.py) с пятью последовательными блоками:
  вставка с commit, чтение, вставка с rollback, проверка отсутствия строки и удаление первой строки.
- Сохранил выданные ID после `flush()` внутри соответствующих блоков и передал эти числа в новые
  экземпляры `Session` для чтения.
- Перед обращением к атрибутам найденного объекта и его удалением проверил результат на `None`.
- Поместил эксперимент в `main()` с защитой `if __name__ == "__main__"`.

Следующий рабочий шаг — согласовать эксплуатационный контракт первой версии и
начать Linux-практику; продолжение большого самостоятельного курса ORM больше
не является условием старта DevOps.
