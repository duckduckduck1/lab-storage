## Git, Linux и рабочее окружение

### Место темы в `lab-storage`

Git хранит воспроизводимую историю изменений проекта. Linux — среда разработки и будущая
основа production-сервера. Поэтому это не вспомогательная настройка, а часть архитектуры и
эксплуатации.

#### Три состояния Git

Git в базовом цикле связывает три области:

1. **Working tree** — файлы на диске, с которыми я работаю.
2. **Index**, или staging area, — подготовленный снимок будущего коммита.
3. **Repository** — граф уже созданных коммитов в `.git`.

`git add` обновляет index содержимым из working tree. `git commit` создаёт новый снимок из index и
передвигает текущую ссылку ветки. `git push` передаёт локальные объекты и обновляет ссылку в удалённом
репозитории.

Удобная модель: working tree — текущее содержимое рабочего стола, index — отобранный набор для
следующего снимка, а commit — уже сохранённый снимок со ссылкой на предыдущий. Коммит хранит состояние,
а `git diff` вычисляет различие между двумя состояниями.

#### Локальная и удалённая история

Git — распределённая система: локальный репозиторий сам хранит историю. GitHub — один из удалённых
сервисов для хранения и совместной работы, а не сам Git. `ahead` означает, что в локальной ветке есть ещё
не отправленные коммиты; `behind` — что в отслеживаемой удалённой ветке есть коммиты, которых нет локально.

Для GitHub пароль учётной записи не используется как Git-пароль. Документированные варианты включают
HTTPS с токеном и SSH. Секрет нельзя класть в коммит: удаление из следующей версии не удаляет его из старой истории.

#### Linux, shell и `PATH`

Shell — командный интерпретатор. Он читает команду, выполняет подстановки и запускает встроенную команду
или отдельный процесс. `PATH` — список каталогов, в которых shell ищет исполняемый файл, если в команде не указан полный
путь.

Обычный запус скрипта создаёт дочерний процесс. Его изменения переменных не меняют родительский shell. `source`
выполняет команды в текущем shell, поэтому изменение `PATH` из `.bashrc` может сразу повлиять на текущую сессию.

Виртуальное окружение Python активируется по той же идее: скрипт добавляет `.venv/bin` в начало `PATH`. Активация
удобна, но не обязательна: можно явно вызывать `.venv/bin/python`.

#### Что хранится в Git

В историю проекта идут исходный код, SQL, тесты и файлы-рецепты окружения. Генерируемые кэши, `.venv`, секреты и
локальные служебные записи не коммитятся. `.gitignore` не удаляет уже отслеживаемый файл: он влияет на неотслеживаемые файлы.

#### Формулировки для собеседования

- Git хранит снимки состояния, а commit ссылается на родителя, формируя граф истории.
- Index позволяет явно собрать следующий коммит независимо от всех изменений working tree.
- GitHub не заменяет Git: Git работает локально, GitHub хранит удалённую копию и даёт инструменты совместной работы.
- `source` меняет текущий shell, а обычный запуск скрипта выполняется в отдельном процессе.

4. Почему `source ~/.bashrc` может изменить `PATH` текущего shell?

## Модель данных и выбор языка

### Место темы в `lab-storage`

Модель данных задаёт словарь предметной области: какие сущности существуют, какие данные они
хранят и как связаны. В `lab-storage` верхний уровень — исследование `Study`, внутри него идут
сессии загрузки `Session`, а к каждой сессии относятся файлы `File`.

Python выбран основным языком приложения и автоматизации. Это позволяет глубоко изучать один
защищаемый на собеседовании язык и применять его сразу в трёх направлениях проекта: backend,
QA automation и DevOps-скрипты. Выбор не означает, что Go хуже; он исключён из текущего учебного
контура, чтобы не распылять время.

#### Класс, экземпляр и атрибут

**Класс** создаёт новый тип объектов и описывает общие для них данные и поведение. **Экземпляр** —
конкретный объект этого класса: например, `Study` является классом, а созданное исследование с
`id=1` — его экземпляром. **Атрибут** — имя внутри объекта, доступное через точку, например
`study.name`.

Класс можно представить как описание формы данных, а экземпляр — как отдельную заполненную форму.
Например, класс `Study` задаёт поля всех исследований, но каждый созданный объект `Study` хранит
собственные значения этих полей.

Метод — функция, связанная с объектом. При вызове `object.method()` Python автоматически передаёт
сам объект первым аргументом метода. По соглашению этот параметр называется `self`; специальным
ключевым словом он не является. Вызов `study.method()` по механике передачи объекта соответствует
вызову функции класса с явным первым аргументом: `Study.method(study)`.

#### Что делает `@dataclass`

`@dataclass` — декоратор класса. Декоратор получает уже созданный объект класса и возвращает
обработанный класс. Модуль стандартной библиотеки `dataclasses` по аннотированным полям генерирует
служебные методы, в том числе `__init__` для начальной инициализации и `__repr__` для отладочного
представления.

`dataclass` сокращает шаблонный код модели, но не превращает аннотации в runtime-проверки. Запись
`id: int` сообщает ожидаемый тип человеку и статическому анализатору; обычный вызов Python сам по
себе не обязан отклонить строку вместо числа.

#### Имена, ссылки и изменяемые объекты

В Python присваивание не копирует объект: оно связывает имя с объектом. Несколько имён могут
ссылаться на один изменяемый список, поэтому изменение через одно имя будет видно через другое.
Это называется **aliasing**, или наличие нескольких ссылок на один объект.

Например, после `first = []` и `second = first` оба имени связаны с одним списком. Поэтому
`second.append(1)` меняет тот же объект, который виден через `first`; присваивание само по себе
не создало второй список.

Изменяемый список нельзя использовать как один общий объект по умолчанию для всех экземпляров.
`field(default_factory=list)` хранит ссылку на фабрику и вызывает `list()` при создании каждого
нового экземпляра. Поэтому у двух исследований будут разные списки `sessions`. Круглые скобки после
`list` здесь отсутствуют намеренно: передаётся функция, а не результат её немедленного вызова.

#### Дерево в памяти и внешние ключи

В памяти удобно собрать дерево: `Study.sessions` содержит объекты `Session`, а `Session.files` —
объекты `File`. Метод `append` добавляет в список ссылку на уже созданный объект. Такое дерево удобно
печатать, отдавать в генератор и обходить вложенными циклами.

Для постоянного хранения используется другая форма связи: дочерняя запись хранит ID родителя.
`Session.study_id` и `File.session_id` — будущие внешние ключи базы. Это похоже на номер записи
в каталоге: ребёнок хранит номер родителя, а не полную копию всех его данных.

Обе формы намеренно присутствуют одновременно:

- вложенные списки дают удобную объектную структуру в оперативной памяти;
- ID позволяют выразить связь в реляционной базе и передавать идентификаторы через API;
- согласованность этих двух представлений должна проверяться тестами и позже обеспечиваться слоем
  работы с базой.

#### Реализация раздела

- [`models.py`](models.py) — Python-модели, фабрики значений по умолчанию и аннотации связей.
- [`main.py`](main.py) — сборка и вложенный обход дерева `Study -> Session -> File`.

#### Формулировки для собеседования

- Класс определяет новый тип, экземпляр хранит состояние конкретного объекта, а `self` — явный
  первый параметр метода, который Python подставляет при вызове через экземпляр.
- `dataclass` генерирует типовой код модели по аннотированным полям, но не выполняет runtime-проверку
  указанных типов.
- Присваивание в Python связывает имя с объектом, а не копирует данные; поэтому изменяемые объекты
  требуют внимания к aliasing.
- `default_factory` создаёт новое изменяемое значение для каждого экземпляра и предотвращает
  совместное использование одного списка.
- Вложенность объектов удобна в памяти, а внешний ключ хранит устойчивую связь между строками в БД.

## Python и автоматизация тестирования

### Место темы в `lab-storage`

Python выполняет две роли: на нём будет написан backend, и им же автоматизируются генерация
синтетических данных, проверки и эксплуатационные задачи. pytest проверяет наблюдаемое поведение,
mypy сопоставляет код с аннотациями типов, а Ruff проверяет стиль и набор статических правил. Эти
инструменты отвечают на разные вопросы и не заменяют друг друга.

#### Модуль и точка входа

Каждый файл `.py` является модулем. При импорте Python создаёт объект модуля и выполняет его код
верхнего уровня. Поэтому исполняемые действия на верхнем уровне могут неожиданно запуститься и в
тестах, которые импортируют функцию.

`__name__` — специальное имя модуля. У непосредственно запущенного файла оно равно `"__main__"`,
а у импортированного — имени модуля. Условие `if __name__ == "__main__":` отделяет определение
функций от запуска программы: импорт предоставляет функции, но не стартует демонстрационный сценарий.

Импорт не копирует текст одного файла в другой. Python загружает и выполняет модуль как объект
времени выполнения, после чего его имена доступны через пространство имён.

#### Функция, результат и раннее завершение

Функция создаётся конструкцией `def`. `return value` немедленно завершает текущий вызов и возвращает
значение. Если выполнение дошло до конца без `return`, результатом будет `None` — отдельный объект,
обозначающий отсутствие значения.

Guard clause — ранняя проверка недопустимого случая. В генераторе каждый отрицательный аргумент
проверяется отдельным `if`, после чего `raise ValueError(...)` немедленно прерывает функцию.
`ValueError` применяется, когда тип аргумента допустим, но само значение не входит в разрешённый
диапазон. После всех guard clauses основной путь можно писать линейно, без большого `else`.

Порядок проверок наблюдаем извне: если одновременно неверны несколько аргументов, вызывающий код
получит исключение от первого сработавшего guard. Поэтому негативный unit-тест меняет одну причину,
иначе он может проверить не тот контракт.

#### Время и фабрики значений

`datetime` может быть timezone-aware — содержать информацию о часовом поясе — или naive, без неё.
Для меток событий проект использует UTC-aware значение. Суффикс `+00:00` означает нулевое смещение
от UTC и делает временную шкалу однозначной между машинами.

В `field(default_factory=utc_now)` передаётся сам объект-функция. `dataclass` вызывает его отдельно
при создании каждого экземпляра. Если вместо этого вычислить время один раз при объявлении класса,
несколько последующих объектов смогут получить одно старое значение.

#### Синтетические и воспроизводимые данные

Генератор создаёт только вымышленные исследования, пользователей и имена файлов. Это позволяет
разрабатывать публичный проект без утечки лабораторных или персональных данных.

Псевдослучайный генератор по начальному состоянию `seed` создаёт воспроизводимую последовательность:
в одной версии реализации одинаковый seed и одинаковый порядок вызовов дают одинаковые выбранные
значения. Локальный объект `Random(seed)` изолирует генератор от глобального состояния модуля
`random`, поэтому чужой вызов не меняет тестовый сценарий. Такая случайность подходит для синтетики
и тестов, но не для паролей, токенов или криптографических ключей.

#### Как устроен unit-тест

Unit-тест проверяет небольшую единицу поведения в изоляции от сети и production-базы. В pytest тест —
обычная функция с именем `test_...`. Внутри используется `assert`: если выражение ложно, тест падает,
а pytest показывает значения частей выражения.

Полезная мысленная структура теста:

1. **Arrange** — подготовить входные данные и ожидаемый результат.
2. **Act** — вызвать проверяемое действие.
3. **Assert** — сравнить наблюдаемый результат с контрактом.

Для исключений применяется `pytest.raises`. Контекстный менеджер подтверждает тип исключения, а
`match` проверяет его сообщение регулярным выражением. Если исключения не было или оно другого типа,
тест падает.

Fixture — подготовленный pytest ресурс, который тест запрашивает аргументом функции. `tmp_path`
передаёт отдельный временный каталог в виде `Path`; тест не выбирает глобальное имя и не оставляет
артефакт в репозитории.

Зелёный тест доказывает только записанные утверждения. Если требование о размере файла отсутствует
в `assert`, тест ничего о размере не подтверждает. Поэтому тестирование включает не только запуск,
но и анализ полноты проверяемого контракта.

#### Границы, классы эквивалентности и уникальность

Класс эквивалентности — группа входов, для которых ожидается одинаковое поведение. Для количества
файлов значения можно разделить как минимум на отрицательные, ноль и положительные. `-1` должен
вызывать ошибку, `0` создавать допустимую пустую коллекцию, положительное число — заданное количество.

Проверка количества и проверка уникальности независимы. Список `[1, 1, 1, 1]` имеет длину четыре,
но множество из него — длину один. Поэтому сравнение `len(ids)` с ожидаемым количеством проверяет
число объектов, а сравнение `len(ids) == len(set(ids))` — отсутствие повторяющихся ID.

List comprehension создаёт список из элементов и выражений цикла. Вложенная форма для файлов
эквивалентна двум циклам: внешний перебирает сессии, внутренний — файлы текущей сессии.

#### Файлы и управление ресурсом

`Path` представляет путь как объект и позволяет соединять компоненты оператором `/`. Само создание
`Path` не создаёт файл. `Path.open("w", encoding="utf-8")` открывает текстовый поток на запись;
режим `w` создаёт файл или обнуляет существующий, а `a` дописывает в конец.

Оператор `with` работает через протокол контекстного менеджера. При входе приобретается ресурс, а
при выходе вызывается завершающая операция и при нормальном выполнении, и при исключении. Для файла
это гарантированное закрытие, встроенное в структуру блока; вручную дублировать `close()` во всех
ветках выполнения не нужно.

#### Типы и инструменты качества

Python динамически типизирован: объект несёт тип во время выполнения, а имя можно позже связать с
объектом другого типа. Аннотации описывают ожидаемый контракт, но интерпретатор обычно не превращает
их в автоматические проверки вызова.

mypy — статический анализатор: он читает исходный код, сопоставляет операции с аннотациями и не
запускает программу. Строгий режим усиливает набор проверок, но mypy не заменяет runtime-валидацию
входных данных и тесты поведения.

Ruff ищет выбранные классы ошибок и проверяет форматирование. `pip check` проверяет, совместимы ли
установленные пакеты по объявленным зависимостям. Разделение файлов зависимостей не даёт pytest и
линтерам без необходимости попасть в production-окружение:

- `requirements.txt` — пакеты, нужные работающему приложению;
- `requirements-dev.txt` — runtime-набор через `-r` плюс инструменты разработки.

Стандартная библиотека (`pathlib`, `random`, `datetime`) поставляется вместе с Python и в список
сторонних зависимостей не записывается.

#### Формулировки для собеседования

- Guard clause завершает функцию на недопустимом входе и оставляет основной сценарий линейным.
- Аннотации Python не обеспечивают runtime-валидацию; mypy проверяет согласованность типов статически.
- Fixture управляет подготовкой и жизненным циклом тестового ресурса, а тест получает его как аргумент.

- Успешный тест подтверждает только явно записанные проверки, поэтому покрытие требований важнее
  одного факта «тест зелёный».

#### Что я понял

- Аннотация типа не проверяет диапазон значения во время выполнения.
- `ValueError` подходит для аргумента правильного типа с недопустимым значением.
- `raise` немедленно прекращает выполнение функции, поэтому порядок guard
  clauses определяет первую наблюдаемую ошибку.
- Граничное значение `0` и ошибочное значение `-1` относятся к разным классам
  эквивалентности и должны проверяться отдельно.
- `len(list)` показывает количество элементов, а `len(set(list))` — количество
  уникальных значений, потому что множество не хранит дубликаты.
- Проверка ожидаемого количества объектов не заменяет проверку уникальности их
  ID: четыре разных объекта могут получить одинаковый ID.
- Вложенный list comprehension для файлов соответствует двум вложенным циклам:
  сначала перебираются сессии, затем файлы текущей сессии.
- Объект `Path` представляет путь, но сам по себе не создаёт и не открывает
  файл; оператор `/` соединяет компоненты пути с учётом платформы.
- Режим `"w"` создаёт или полностью перезаписывает файл, а `"a"` сохраняет
  существующее содержимое и добавляет данные в конец.
- Контекстный менеджер гарантирует завершение работы с ресурсом: выход из блока
  `with` закрывает файл даже при исключении.
- Зелёный тест подтверждает только реализованные утверждения, а не все
  требования: отсутствующая проверка способна скрыть дефект.
- Модули стандартной библиотеки, включая `pathlib`, поставляются с Python и не
  записываются в requirements-файлы.
- Runtime-зависимости нужны работающему приложению, а pytest, Ruff и другие
  development-инструменты не должны без необходимости попадать в production.
- `-r` в requirements-файле подключает другой файл, поэтому development-набор
  может включать весь runtime-набор без дублирования.
- Прямые зависимости выбирает проект, а транзитивные устанавливаются потому,
  что нужны прямым зависимостям.
- Успешные тесты подтверждают поведение, но не гарантируют, что код уже
  отрефакторен: структуру нужно дополнительно читать и проверять.

## PostgreSQL и SQL

### Место PostgreSQL в `lab-storage`

PostgreSQL хранит метаданные: исследования, сессии загрузки и описания файлов. Сами
большие файлы будут лежать на диске. Такое разделение позволяет реляционной базе проверять
связи и искать записи, не превращая её в хранилище многогигабайтных бинарных объектов.

Реляционная модель представляет данные в виде таблиц. Строка — один экземпляр сущности, столбец —
один её атрибут. В памяти Python связь `Study -> Session -> File` можно собрать как вложенное дерево. В базе
дочерняя строка хранит не весь объект родителя, а его ID: по этому номеру PostgreSQL находит запись
родителя в центральной таблице.

#### Ограничения как инварианты

Ограничение, или constraint, — правило, которое PostgreSQL проверяет при изменении данных. Это инвариант:
условие, которое должно оставаться истинным для любого допустимого состояния базы.

Валидация в Python всё равно нужна для хорошего ответа API, но она не заменяет ограничения схемы. В базу
может писать не только API, но и миграция, тест, `psql` или администратор. Поэтому недостаточно
проверить данные в одной Python-функции: инвариант нужно защитить и на границе самой базы.

| Ограничение | Что гарантирует | Пример в проекте | SQLSTATE нарушения |
| --- | --- | --- | --- |
| `NOT NULL` | Значение обязательно | `studies.name` | `23502` |
| `PRIMARY KEY` | Строка имеет уникальный непустой ID | `studies.id` | `23505` для дубликата |
| `FOREIGN KEY` | У дочерней строки есть существующий родитель | `sessions.study_id` | `23503` |
| `CHECK` | Логическое условие не ложно | `size_bytes >= 0` | `23514` |

SQL использует трёхзначную логику: `TRUE`, `FALSE` и `UNKNOWN`. Для `NULL` выражение `size_bytes >= 0` даёт
`UNKNOWN`, а `CHECK` отклоняет только `FALSE`. Поэтому `CHECK (size_bytes >= 0)` и `NOT NULL` решают разные задачи и нужны
одновременно.

#### ID, identity и `RETURNING`

`GENERATED ALWAYS AS IDENTITY` поручает PostgreSQL генерировать ID. При параллельных вставках последовательность
атомарно выдаёт разные значения. Но эти значения не обещают быть без пропусков: откат транзакции не
возвращает уже выданное значение обратно. ID — это идентификатор, а не порядковый номер без дыр.

`INSERT ... RETURNING id` возвращает ID строки, созданной этой же командой. Отдельный `SELECT max(id)` не равноценен:
между `INSERT` и `SELECT` другой клиент может вставить новую строку, и первый клиент получит чужой ID.

#### Транзакции в негативных проверках

Транзакция группирует изменения в операцию «всё или ничего». `COMMIT` фиксирует результат, `ROLLBACK`
отменяет изменения. После ошибки внутри транзакции PostgreSQL считает её аварийно завершённой; вернуть
управление можно полным `ROLLBACK` или откатом к заранее созданной точке сохранения.

В [`sql/check_constraints.sql`](sql/check_constraints.sql) каждая намеренно неверная вставка запускается в отдельной транзакции.
`\set ON_ERROR_STOP off` временно говорит клиенту `psql` продолжить чтение файла после ожидаемой ошибки; сами
ограничения сервера эта метакоманда не отключает.

#### Лексические правила SQL

- `;` завершает SQL-команду.
- `'text'` — строковая константа.
- `"name"` — кавыченный SQL-идентификатор, например точное имя столбца.
- В выражении `source_column AS output_label` слева находится источник значения,
  а справа создаётся временная метка столбца результата. `AS` не изменяет схему
  и не требует, чтобы `output_label` уже существовал в таблице.
- Скалярный подзапрос — `SELECT` в скобках, возвращающий один столбец и не более одной строки. Его
  результат можно использовать там, где ожидается одно значение.

  на временной сессии без файлов.

#### Формулировки для собеседования

- Ограничения базы защищают инварианты независимо от того, какой клиент изменяет данные.
- Внешний ключ обеспечивает ссылочную целостность: нельзя создать дочернюю строку с несуществующим
  родителем.
- `RETURNING` получает сгенерированный ID из той же операции вставки и устраняет гонку, возможную при
  отдельном `SELECT max(id)`.
- SQLSTATE — стабильный машиночитаемый код ошибки. Клиентский код может проверять его так же,
  как Python-код проверяет конкретный тип исключения, не разбирая текст сообщения для человека.

### 2026-08-03 — Действия внешнего ключа при удалении

#### Термины и поведение

Referential action, или действие внешнего ключа, определяет судьбу дочерних
строк при удалении либо изменении ключа родителя. Действие записывается в
определении внешнего ключа ребёнка, хотя запускает его операция над родителем.

- `NO ACTION` используется по умолчанию и не позволяет оставить нарушенную
  ссылку. Проверку можно отложить, если ограничение допускает отложенную
  проверку.
- `RESTRICT` также запрещает удаление родителя с детьми, но проверяется сразу и
  не может быть отложено.
- `CASCADE` удаляет связанные дочерние строки в той же транзакции.
- `SET NULL` оставляет ребёнка и обнуляет внешний ключ, поэтому несовместим по
  смыслу с обязательной ссылкой `NOT NULL`.
- `SET DEFAULT` подставляет значение по умолчанию, которое всё равно обязано
  удовлетворять внешнему ключу.

Каскад может пройти несколько уровней. Если `sessions.study_id` и
`files.session_id` имеют `ON DELETE CASCADE`, удаление исследования удаляет его
сессии, а удаление этих сессий — их файлы. Все изменения принадлежат одной
транзакции и возвращаются после `ROLLBACK`.

#### Инженерное решение для `lab-storage`

В постоянной схеме пока сохранено стандартное `NO ACTION`. Метаданные файла
находятся в PostgreSQL, а сам файл будет лежать на диске. Каскад базы не удаляет
физический файл и не может атомарно откатить операцию файловой системы. Поэтому
постоянное поведение удаления будет выбрано вместе со сценарием очистки диска,
а не только ради удобства удаления строк.

#### Что я реализовал

- Создал [`sql/on_delete.sql`](sql/on_delete.sql) с временной цепочкой
  `cascade_studies -> cascade_sessions -> cascade_files`.
- Задал `ON DELETE CASCADE` на обоих внешних ключах дочерних таблиц.
- Создал одно исследование, две сессии и три файла, получая identity-ID через
  `RETURNING ... \gset`, а не фиксируя значения вручную.
- Удалил только исследование внутри транзакции и проверил автоматическое
  удаление обоих уровней детей.
- Выполнил `ROLLBACK` и проверил восстановление всего дерева.

#### Ошибки и разбор

| Симптом | Причина | Исправление | Общее правило |
| --- | --- | --- | --- |
| Первый счётчик показывал два исследования вместо одного | После `RETURNING id AS study_id` стоял `;`, а следующая `\gset` повторно отправила тот же `INSERT` серверу | Убрал `;` перед `\gset` | При сохранении результата в переменные `psql` метакоманда `\gset` отправляет запрос и заменяет завершающую точку с запятой |

#### Проверенный результат

- До удаления счётчики исследований, сессий и файлов равнялись `1/2/3`.
- Один `DELETE` исследования вернул `DELETE 1`; внутри транзакции все три
  счётчика стали равны нулю.
- После `ROLLBACK` счётчики восстановились до `1/2/3`, включая строки,
  удалённые PostgreSQL каскадно.
- Постоянные таблицы `studies`, `sessions` и `files` сохранили количества
  `1/2/3`.
- Временные таблицы исчезли после завершения подключения `psql`.

#### Что я понял

- Для многоуровневого каскада действие должно быть допустимо на каждом звене
  цепочки внешних ключей.
- Если удаление исследования каскадно пытается удалить сессии, но файлы
  защищают эти сессии стандартным `NO ACTION`, PostgreSQL отклонит всю исходную
  команду `DELETE`.
- Ошибка на нижнем уровне не оставит дерево частично удалённым: изменения одной
  SQL-команды атомарны.

#### Вопросы для самопроверки

1. На каком внешнем ключе нужно писать `ON DELETE CASCADE`, чтобы удаление
   исследования удаляло его сессии?
2. Почему каскадное удаление строк `files` не решает удаление настоящих файлов
   с диска?
3. Почему `ROLLBACK` восстановил не только исследование, но и автоматически
   удалённые дочерние строки?

| В `GROUP BY` указал `joined_row_count` и `file_count` | Счётчики являются результатами агрегирования, а не признаками, по которым создаются группы | Сгруппировал по `s.id` и `s.note` | Сначала строки разделяются на группы по исходным выражениям, затем для каждой группы вычисляются агрегаты |

#### Проверенный результат

- Для созданной пустой сессии `INNER JOIN` вернул ноль строк.
- `LEFT JOIN` вернул одну строку с данными сессии и значениями `[NULL]` в
  `file_id` и `file_name`.
- Агрегатный запрос вернул счётчики `2/2` и `1/1` для сессий с файлами, а для
  пустой сессии — `joined_row_count = 1` и `file_count = 0`.
- `HAVING` отфильтровал уже сформированные группы и вернул только первую сессию
  со значением `file_count = 2`.
- После `ROLLBACK` запрос `count(*)` подтвердил отсутствие тестовой сессии.

#### Что я понял

- `LEFT JOIN` сохраняет строки таблицы, написанной слева от слов `LEFT JOIN`.
- В конструкции `studies LEFT JOIN sessions` гарантированно сохраняются
  исследования, а не каждая сессия.
- Последующий обычный `JOIN files` требует совпавший файл и поэтому способен снова
  удалить пустую сессию. Для сохранения всех сессий нужна конструкция
  `sessions LEFT JOIN files`.
- `count(*)` считает все строки группы, включая созданную `LEFT JOIN` строку с
  отсутствующим файлом.
- `count(f.id)` считает только ненулевые значения `f.id`; у пустой сессии одна
  результирующая строка, но `f.id` в ней равен `NULL`, поэтому количество файлов
  равно нулю.
- `WHERE` фильтрует отдельные строки до `GROUP BY`, когда агрегатные значения ещё
  не вычислены.
- `HAVING` фильтрует уже сформированные группы и поэтому может проверять условие
  вида `count(f.id) >= 2`.

### 2026-08-02 — Ограничение `UNIQUE`

#### Термины и поведение

`UNIQUE` — ограничение целостности, запрещающее повторение значения или
комбинации значений в разных строках. В отличие от `PRIMARY KEY`, оно защищает
дополнительный бизнес-ключ: у таблицы может быть несколько ограничений
`UNIQUE`, но только один первичный ключ. В PostgreSQL ограничение автоматически
создаёт уникальный B-tree индекс.

Столбцовая запись `username text NOT NULL UNIQUE` одновременно задаёт тип,
обязательность значения и его уникальность. Табличная форма
`UNIQUE (first_column, second_column)` проверяет уникальность всей пары, а не
каждого столбца отдельно. По умолчанию два `NULL` не считаются равными для
`UNIQUE`; сочетание с `NOT NULL` исключает эту неоднозначность для обязательного
бизнес-ключа.

Нарушение уникальности имеет SQLSTATE `23505`. Проверка в Python полезна для
понятного ответа API, но только ограничение базы защищает правило от всех
клиентов и одновременных операций.

#### Принятое решение

В постоянную схему `studies`, `sessions` и `files` ограничение пока не добавлено.
Уникальность названия исследования или имени файла внутри сессии ещё не
подтверждена требованиями лаборатории. Ограничение, не отражающее реальное
бизнес-правило, способно запретить допустимые данные. Поведение проверено на
временной таблице будущих пользователей, где уникальное имя входа является
понятным примером инварианта.

#### Что я реализовал

- Создал [`sql/unique_constraint.sql`](sql/unique_constraint.sql) с временной
  таблицей `synthetic_users`.
- Сделал `username` обязательным и уникальным.
- Временно отключил остановку `psql` только вокруг намеренной повторной
  вставки, не отключая само ограничение PostgreSQL.
- После ошибки вставил другое имя и вывел итоговые строки по ID.

#### Ошибки и разбор

| Симптом | Причина | Исправление | Общее правило |
| --- | --- | --- | --- |
| `42601` около `/` в первой строке | Метакоманда `psql` начиналась с `/set`, а не с `\set` | Использовал обратную косую черту | Метакоманды клиента начинаются с `\` и не являются SQL-командами |
| `42P01: relation "sythetic_users" does not exist` | Имя созданной таблицы `synthetic_users` отличалось от имени в `INSERT` одной пропущенной буквой | Привёл все обращения к одному идентификатору | Имена таблиц и столбцов должны буквально совпадать со схемой |

#### Проверенный результат

#### Что я понял

- Составное ограничение `UNIQUE (session_id, name)` сравнивает пару значений
